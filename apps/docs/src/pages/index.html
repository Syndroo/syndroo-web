Publish from your own agent, on your own infrastructure.

Syndroo is an open-source HTTP API. It accepts a post, stores one publication per selected platform, delivers text through Cloudflare Queues and Cron Triggers, and records what each platform did. You host it: the Cloudflare account, the database and the platform credentials are yours.

What Syndroo is

Syndroo is a small npm-workspaces monorepo with a Worker in front of Cloudflare D1, Queues and a Cron Trigger. It accepts immediate or scheduled posts, keeps one publication row per platform, and reports each platform's own outcome.

  • HTTP API service. There is no dashboard, no account with the project, and no hosted service. You deploy the Worker, then call its URL from curl, an agent, a script or your own application.
  • Self-hosted. You own the Cloudflare account, D1 database, Queue, Cron Trigger and platform credentials.
  • Text only. Every adapter in this candidate publishes text. Media, per-request authors, OAuth login flows and token refresh are outside this version, so credential renewal is your job.
  • One public package, not published yet. @syndroo/cloudflare-worker is the only public package, and this candidate has not been published. The other workspace packages, including @syndroo/core, are internal implementations rather than public SDKs.
  • No Syndroo skill, plugin or MCP server. Agent setup means wiring your own client to the documented HTTP API; nothing is installable from the project yet.

How it runs

The deployed Worker is the whole runtime. It keeps a Bearer-authenticated HTTP surface in front of D1 and a Queue producer, and it handles two background paths.

  1. Admission

    POST /v1/posts validates the request and the platform configuration, then writes the post and one publication row per selected platform into D1. The reply is HTTP 202 with status: "queued" or "scheduled".

  2. Delivery

    Immediate posts go to Cloudflare Queues. A Queue consumer claims one publication atomically before the outbound platform request, so one platform's failure does not stop the others.

  3. Scheduling and recovery

    A Cron Trigger scans every 15 minutes for due posts and for stale jobs. A scheduled time in the past is handled as an immediate post.

  4. Inspection

    GET /v1/posts and GET /v1/posts/<id> read the stored state, including one publication entry per platform with its status, error code and identifier.

Read Delivery and guarantees before you build automation on top of the API. Queue delivery is at least once, retries are bounded, and an ambiguous platform result is never resent automatically.

Recipes

Each recipe states its inputs, the exact request, the expected responses, and what to do when a platform fails.

  • Publish a product update - one release note, per-platform wording, and a result you can read afterwards.
  • Publish a blog summary - your own client writes the summary; Syndroo publishes it.
  • Call Syndroo from CI or a script - stable idempotency keys and polling until a terminal state.

These recipes are written for the 0.2.0-rc.1 HTTP contract. They do not assume a dashboard, an SDK or an agent skill.
