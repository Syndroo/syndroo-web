Publish your first post

This path uses one platform (Bluesky) and one credential set. It ends with a published post whose per-platform status you have read back from the API. The commands below publish for real once credentials are configured, so use an account you are happy to post from.

These commands publish for real.

Once Bluesky credentials are configured, a copied POST /v1/posts request creates a live post. The demo on the marketing site is simulated; this page is not. Nothing on this page runs until you paste it into your own terminal.

Before you start

  • A Worker that answers requests. Either a deployment in your own Cloudflare account (Cloudflare deployment) or a local instance (Local development). The two paths are separate: deployment does not require the local steps, and local development does not require a Cloudflare account.
  • A Bluesky account and an app password. Use an app password, never your account password. The Bluesky guide lists the exact secret names.
  • The API key you chose. SYNDROO_API_KEY is the Bearer token every client sends. Treat it as a password: anyone who has it can publish through your Worker.

Steps

  1. Configure the platform credentials

    Add the Bluesky values next to SYNDROO_API_KEY in the place your runtime reads secrets from: Worker secrets for a deployment, .dev.vars for local development. The names are the same in both places.

    BLUESKY_IDENTIFIER=your-handle.bsky.social
BLUESKY_PASSWORD=your-bluesky-app-password
BLUESKY_HOST=bsky.social

    BLUESKY_HOST is optional and defaults to bsky.social. Only Bluesky is needed for this page; leave every other platform's credentials unset.

    Platforms are enabled independently.

    A missing or incomplete credential set returns HTTP 422 with PLATFORM_NOT_CONFIGURED before anything is stored or queued. A deployment with no platform credentials can still answer health checks, but it cannot accept posts.

  2. Check the service

    The health endpoint needs no authentication. Set the two variables in the terminal that will call Syndroo.

    export SYNDROO_URL="https://your-worker.your-subdomain.workers.dev"
export SYNDROO_API_KEY="the-same-secret-your-worker-has"
curl "$SYNDROO_URL/health"

    Expected response:

    {"status":"ok"}

    For a local instance the URL is http://localhost:8787. /health always answers 200 with that body, even while maintenance mode is on: it needs no API key and is checked before anything else. Maintenance mode affects only POST /v1/posts, which then returns 503 with SERVICE_UNAVAILABLE; reads keep working.

  3. Publish one Bluesky post

    Send one request with a stable idempotency key. The key ties this one logical post to this one request, so a retry cannot publish twice.

    curl -X POST "$SYNDROO_URL/v1/posts" \
  -H "Authorization: Bearer $SYNDROO_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: first-post-001" \
  --data '{
    "content": "First post through my own Syndroo Worker.",
    "platforms": ["bluesky"]
  }'

    The reply is an acceptance receipt rather than a delivery report, so it is HTTP 202:

    {
  "id": "post_...",
  "status": "queued"
}

    queued means the post was accepted and still has publications waiting. It does not confirm Bluesky's outcome, and it is not proof that Bluesky has not published already: read publications to see what each platform actually did.

  4. Read the result

    Request the post until it reaches a terminal status. published and failed are terminal; queued and publishing are not.

    curl \
  -H "Authorization: Bearer $SYNDROO_API_KEY" \
  "$SYNDROO_URL/v1/posts/post_..."

    A successful publication looks like this. The aggregate status is published only when every selected platform succeeded.

    {
  "id": "post_...",
  "content": "First post through my own Syndroo Worker.",
  "platforms": ["bluesky"],
  "status": "published",
  "publications": [
    {
      "platform": "bluesky",
      "provider": "bluesky-native",
      "status": "published",
      "attempts": 1,
      "externalId": "at://did:plc:.../app.bsky.feed.post/...",
      "externalUrl": "https://bsky.app/profile/.../post/...",
      "errorAmbiguous": false
    }
  ]
}

    Other outcomes you can meet here:

    StatusWhat it meansWhat to do
    publishingClaimed by a Queue consumer; the platform call is still running.Poll again shortly. Do not send a new request.
    publishedBluesky confirmed the post and returned an identifier.Nothing. If an externalUrl is present, that is the post link the platform returned.
    failed, errorAmbiguous: falseStopped after a terminal failure, or after the retry budget was exhausted. Read errorCode, errorMessage and attempts.Only after confirming errorAmbiguous is false, fix the cause and send a new request with a new key. That decision is yours; Syndroo resends nothing.
    failed with errorAmbiguous: trueThe write may have reached the platform; the outcome is unknown.Check the account by hand first. Syndroo never resends an ambiguous publication automatically.

Where to go next

  • Add a second platform. Configure that platform's credentials and add its name to platforms. Each guide lists its own secret names and limits.
  • Schedule instead of posting now. Add "scheduledAt": "2030-01-02T03:04:05.000Z" with an explicit timezone. Cron scans for due posts on a 15-minute cadence, and queue and platform time are added on top, so the requested time is not an exact publication time and no end-to-end bound is promised.
  • Let an agent drive it. Agent setup explains the exact HTTP workflow, including the preview and confirmation step that belongs to your client rather than the API.
  • Automate it. Call Syndroo from CI or a script shows keys derived from a commit and polling until a terminal state.

Common failures

SymptomCauseWhat to do
HTTP 401Missing or incorrect Bearer token.Send Authorization: Bearer $SYNDROO_API_KEY with the same value the Worker has.
HTTP 415The body is not sent as JSON.Add Content-Type: application/json.
HTTP 413The request body exceeds 64 KiB.Shorten the request. Platform text limits are far smaller than this ceiling.
HTTP 422Bluesky is not configured, or a credential is missing.Add BLUESKY_IDENTIFIER and BLUESKY_PASSWORD, then restart or redeploy.
HTTP 409The Idempotency-Key was used with different content.Use a new key for a genuinely different post, or resend the original body to get the original result back.
Publication failed with INVALID_CONTENTThe text passed the API but exceeded the platform's own limit.Shorten the text. The candidate enforces 300 Unicode code points and 3,000 UTF-8 bytes for Bluesky before the network call.
errorAmbiguous: trueA timeout or a post-stage 5xx left the remote outcome unknown.Check the account manually. Syndroo does not resend ambiguous publications automatically.
