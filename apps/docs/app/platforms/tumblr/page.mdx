        <h1 id="tumblr-setup">Tumblr setup</h1>
        <p className="lede">Tumblr uses native HTTP with OAuth 1.0a signing. You register an application, finish the authorization flow yourself, and store four OAuth values plus the target blog name in the Worker.</p>
        <div className="status-strip" aria-label="Tumblr status recorded for 0.2.0-rc.1">
          <span className="status-chip"><span className="status-dot experimental"></span>Experimental</span>
          <span className="status-chip">Provider <code>{"tumblr-native"}</code></span>

        <h2 id="status">Status and evidence</h2>
        <p>Syndroo <code>{"0.2.0-rc.1"}</code> is an unpublished release candidate: prepared in the repository, not published to npm, not tagged, and not deployed. Tumblr is recorded as <strong>experimental</strong> for this candidate.</p>
        <p>Evidence: unit tests and the approved native-HTTP spike recorded in the core repository. The SDK route was rejected earlier because it lacked cancellation and response-size controls, so the adapter signs its own requests. There is no Mock SNS end-to-end coverage for Tumblr, and no live-account acceptance record exists. See <a href="/concepts/#platform-readiness">Platform readiness</a> and the <a href="/#facts-source">capability record</a>.</p>

        <h2 id="prerequisites">What you need</h2>
        <ul>
          <li><strong>A Tumblr account</strong> you can post from, and the blog you intend to publish to.</li>
          <li><strong>A registered Tumblr OAuth application</strong> that gives you a consumer key and secret.</li>
          <li><strong>The completed OAuth 1.0a authorization</strong> for that account, which yields the user token and token secret. Syndroo does not run this flow; you finish it once, outside the Worker.</li>
          <li><strong>A running Worker and its API key.</strong> Either <a href="/operations/cloudflare/">a deployment in your own Cloudflare account</a> or <a href="/operations/local/">a local instance</a>. The Worker holds the platform credentials; clients hold only <code>{"SYNDROO_API_KEY"}</code>. If you have not set one up yet, the <a href="/quickstart/">first-post walkthrough</a> covers the whole path with Bluesky.</li>
        </ul>
        <p>The adapter reads five Worker secrets:</p>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">Secret</th><th scope="col">Required</th><th scope="col">Value</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row"><code>{"TUMBLR_CONSUMER_KEY"}</code></th><td>Yes</td><td>OAuth consumer key of your registered application.</td></tr>
              <tr><th scope="row"><code>{"TUMBLR_CONSUMER_SECRET"}</code></th><td>Yes</td><td>OAuth consumer secret of that application.</td></tr>
              <tr><th scope="row"><code>{"TUMBLR_TOKEN"}</code></th><td>Yes</td><td>User OAuth token from the completed authorization.</td></tr>
              <tr><th scope="row"><code>{"TUMBLR_TOKEN_SECRET"}</code></th><td>Yes</td><td>Secret paired with that user token.</td></tr>
              <tr><th scope="row"><code>{"TUMBLR_BLOG"}</code></th><td>Yes</td><td>The target blog name, for example <code>{"alice"}</code>. Not a URL.</td></tr>
            </tbody>
          </table>
        </div>
        <p>All five are required, and the authorized user must be able to post to that blog. The blog value is validated when the Worker reads it, so a URL is rejected instead of being sent as a blog identifier.</p>

        <h2 id="credentials">Register the application and authorize</h2>
        <p>The Tumblr OAuth application page and its registration form are Tumblr's; keep the official documentation linked under <a href="#sources">Official sources</a> open while you work. The documented flow is OAuth 1.0a with the HMAC-SHA1 signature method, and registering the application is what issues your consumer key.</p>
        <ol className="steps">
          <li>
            <h3 id="register-app">Register an OAuth application</h3>
            <p>Sign in to Tumblr, open the OAuth applications page and register an application. Registration issues the consumer key and secret for that application.</p>
          </li>
          <li>
            <h3 id="authorize-user">Complete the OAuth 1.0a authorization</h3>
            <p>Run the OAuth 1.0a flow for the account you will publish from and approve write access for the target blog. This produces the user token and token secret. You run this step yourself, once; Syndroo only signs requests with the values you store.</p>
          </li>
          <li>
            <h3 id="confirm-blog">Confirm the target blog</h3>
            <p>Note the blog's short name, which is what the API expects, and confirm from the Tumblr client that the authorizing account can publish to it. A secondary blog the account cannot post to will fail later, after a request has been accepted.</p>
          </li>
        </ol>
        <div className="callout warn">
          <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" strokeWidth="2" strokeLinecap="round" aria-hidden="true"><path d="M12 9v4" /><path d="M12 17h.01" /><path d="M10.3 3.9 1.8 18a2 2 0 0 0 1.7 3h17a2 2 0 0 0 1.7-3L13.7 3.9a2 2 0 0 0-3.4 0Z" /></svg>
          <div>
            <span className="callout-title">Token revocation is your responsibility.</span>
            <p>Tumblr can revoke application or user tokens, and you can revoke them yourself in account settings. When that happens the Worker keeps the old value until you replace it, and publishing fails with <code>{"errorCode"}</code> <code>{"AUTH"}</code> instead of renewing anything.</p>
          </div>
        </div>

        <h2 id="configure">Add the secrets to the Worker</h2>
        <p>Put the values where your runtime reads secrets: Worker secrets for a deployment, <code>{".dev.vars"}</code> for a local instance. <a href="/operations/cloudflare/">Cloudflare deployment</a> and <a href="/operations/local/">Local development</a> cover the exact commands for each path.</p>
        <pre data-label="Tumblr secrets"><code>{"TUMBLR_CONSUMER_KEY=\"your-tumblr-consumer-key\"\nTUMBLR_CONSUMER_SECRET=\"your-tumblr-consumer-secret\"\nTUMBLR_TOKEN=\"your-tumblr-user-token\"\nTUMBLR_TOKEN_SECRET=\"your-tumblr-user-token-secret\"\nTUMBLR_BLOG=\"alice\""}</code></pre>
        <div className="callout info">
          <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" strokeWidth="2" strokeLinecap="round" aria-hidden="true"><circle cx="12" cy="12" r="9" /><path d="M12 16v-5" /><path d="M12 8h.01" /></svg>
          <div>
            <span className="callout-title">Configuration is checked for shape, not for validity.</span>
            <p>Before accepting a post, Syndroo checks that every required value exists, is non-empty and looks like a blog name. It does not call Tumblr to test the credentials. Revoked or under-scoped values pass that check and surface later as a publication failure with <code>{"errorCode"}</code> <code>{"AUTH"}</code>.</p>
          </div>
        </div>

        <h2 id="first-post">Publish and check one post</h2>
        <p>The commands below publish for real once the secrets above are configured. Set the two client variables in the terminal that will call Syndroo.</p>
        <pre data-label="terminal"><code>{"export SYNDROO_URL=\"https://your-worker.your-subdomain.workers.dev\"\nexport SYNDROO_API_KEY=\"the-same-secret-your-worker-has\""}</code></pre>
        <div data-code-scope="publish">
          <pre data-label="POST /v1/posts"><code>{"curl -X POST \"$SYNDROO_URL/v1/posts\" \\\n  -H \"Authorization: Bearer $SYNDROO_API_KEY\" \\\n  -H \"Content-Type: application/json\" \\\n  -H \"Idempotency-Key: tumblr-setup-001\" \\\n  --data '{\n    \"content\": \"First post from my own Syndroo Worker.\",\n    \"platforms\": [\"tumblr\"]\n  }'"}</code></pre>
        </div>
        <p>The accepted response is HTTP <code>{"202"}</code> with status <code>{"queued"}</code>:</p>
        <pre data-label="202 Accepted"><code>{"{\n  \"id\": \"post_...\",\n  \"status\": \"queued\"\n}"}</code></pre>
        <p>HTTP <code>{"202"}</code> means the request was accepted for processing. It does not confirm that Tumblr accepted anything, and it does not prove that the Queue has not already sent the platform request, because delivery can start immediately after acceptance. Read the stored state to learn the outcome:</p>
        <pre data-label="terminal"><code>{"curl \\\n  -H \"Authorization: Bearer $SYNDROO_API_KEY\" \\\n  \"$SYNDROO_URL/v1/posts/post_...\""}</code></pre>
        <pre data-label="200 OK"><code>{"{\n  \"id\": \"post_...\",\n  \"content\": \"First post from my own Syndroo Worker.\",\n  \"platforms\": [\"tumblr\"],\n  \"status\": \"published\",\n  \"publications\": [\n    {\n      \"platform\": \"tumblr\",\n      \"provider\": \"tumblr-native\",\n      \"status\": \"published\",\n      \"attempts\": 1,\n      \"externalId\": \"700000000000000000\",\n      \"errorAmbiguous\": false\n    }\n  ]\n}"}</code></pre>
        <p><code>{"queued"}</code> and <code>{"publishing"}</code> are not terminal; poll the same URL. <code>{"published"}</code> and <code>{"failed"}</code> are terminal. Repeating the identical request with the same <code>{"Idempotency-Key"}</code> returns the stored result with HTTP <code>{"200"}</code> instead of creating a second post. See <a href="/api/#idempotency-header">Idempotency-Key</a>.</p>

        <h2 id="limits">Limits, tokens and external dependencies</h2>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">Item</th><th scope="col">Recorded for 0.2.0-rc.1</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row">Text limit</th><td>4,096 Unicode code points in a single NPF text block, validated before the network call.</td></tr>
              <tr><th scope="row">Content type</th><td>Text only. HTML and Markdown are sent as plain text rather than interpreted, and media, tags, drafts and reblogs are outside this version.</td></tr>
              <tr><th scope="row">Credential maintenance</th><td>Yours. Re-run the authorization or register a new application if Tumblr revokes access, then replace the Worker secrets. Syndroo has no OAuth flow and does not renew tokens.</td></tr>
              <tr><th scope="row">External dependency</th><td>Tumblr's own terms and rate limits apply, including the documented per-user daily posting limit that answers with <code>{"429"}</code> when it is exceeded. Syndroo controls none of them, includes no pricing of its own, and makes no promise about a provider's current plan, quota or API behaviour.</td></tr>
            </tbody>
          </table>
        </div>
        <p>Check the provider's current documentation before relying on a specific limit, endpoint or authorization detail. Those facts change on the provider's schedule, not on this page; the links under <a href="#sources">Official sources</a> are the references to re-check.</p>

        <h2 id="failures">When something fails</h2>
        <p>A failed publication stores <code>{"errorCode"}</code>, <code>{"errorMessage"}</code> and <code>{"errorAmbiguous"}</code> in the post response. Read them before you act.</p>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">What you see</th><th scope="col">What it means</th><th scope="col">What to do</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row">HTTP <code>{"422"}</code> <code>{"PLATFORM_NOT_CONFIGURED"}</code></th><td>One of the five Tumblr secrets is missing or empty, or the blog value looks like a URL.</td><td>Add the secrets named above with a blog name, not a link, then send the request again. Nothing was stored or queued.</td></tr>
              <tr><th scope="row"><code>{"AUTH"}</code></th><td>Tumblr rejected the OAuth values, or the account cannot post to that blog.</td><td>Re-run the authorization for the right account and blog, update the Worker secrets, and check the blog before resending.</td></tr>
              <tr><th scope="row"><code>{"INVALID_CONTENT"}</code></th><td>The text exceeded the code-point limit, or the request was otherwise not postable, and nothing was sent.</td><td>Shorten the text and publish again with a new key.</td></tr>
              <tr><th scope="row"><code>{"RATE_LIMIT"}</code></th><td>Tumblr asked the caller to slow down.</td><td>Syndroo retries this automatically with backoff, up to three attempts. Let it finish, then poll the same post.</td></tr>
              <tr><th scope="row"><code>{"PROVIDER_UNAVAILABLE"}</code>, <code>{"NETWORK"}</code> or <code>{"UNKNOWN"}</code>, with <code>{"errorAmbiguous: true"}</code></th><td>The write may have reached Tumblr; the outcome is unknown.</td><td>Check the blog by hand. Syndroo never resends an ambiguous publication automatically.</td></tr>
              <tr><th scope="row">Post status <code>{"partial"}</code></th><td>Some selected platforms succeeded and some failed.</td><td>Never resubmit the platforms that succeeded. The failed ones need attention only after you have excluded an ambiguous outcome.</td></tr>
            </tbody>
          </table>
        </div>
        <div className="callout warn">
          <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" strokeWidth="2" strokeLinecap="round" aria-hidden="true"><path d="M12 9v4" /><path d="M12 17h.01" /><path d="M10.3 3.9 1.8 18a2 2 0 0 0 1.7 3h17a2 2 0 0 0 1.7-3L13.7 3.9a2 2 0 0 0-3.4 0Z" /></svg>
          <div>
            <span className="callout-title">Rule out an ambiguous outcome before publishing again.</span>
            <p>If a publication is <code>{"failed"}</code> with <code>{"errorAmbiguous: true"}</code>, check the blog by hand first, because the post may already exist. Only when you have confirmed that nothing was published and you still want the post should you send a new request with a new <code>{"Idempotency-Key"}</code>. Reusing the old key replays the stored result instead of publishing. Read <a href="/concepts/#ambiguous-outcomes">Ambiguous outcomes</a> for the reasoning.</p>
          </div>
