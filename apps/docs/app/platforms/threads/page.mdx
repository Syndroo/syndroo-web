    <h1 id="threads">Threads</h1>

    <h2 id="overview">Overview</h2>
    <p>Provider id <code>{"threads"}</code>. Metadata documents a two-step publish: create a text container, then publish it. The provider takes the documented one-call path instead, sending{" "} <code>{"media_type=TEXT"}</code> together with <code>{"auto_publish_text=true"}</code>, so a text post is created and published by one request.</p>

    <h2 id="requirements">Requirements</h2>
    <ul>
      <li>A Meta app with the Threads use case, and its client id and client secret.</li>
      <li>A registered redirect URI that the authorization step can return to.</li>
      <li>A Threads account that has authorized the app.</li>
    </ul>

    <p>The authorization code is exchanged at the API host, and a long-lived token is requested at the documented 60-day exchange. The token is what the connection stores.</p>

    <h2 id="connect">Connect</h2>
    <p><code>{"redirectUri"}</code> is required, and the two hosts default to the values published by Meta, so a caller that supplies one host cannot silently mix the pair:</p>
    <pre data-label="connect.json"><code>{"{\n  \"type\": \"start\",\n  \"provider\": \"threads\",\n  \"options\": { \"redirectUri\": \"https://example.com/oauth/callback/threads\" }\n}"}</code></pre>
    <pre data-label="terminal"><code>{"syndroo connect --input connect.json --json"}</code></pre>
    <p>With no options the two hosts are <code>{"https://www.threads.net"}</code> for authorization and <code>{"https://graph.threads.net"}</code> for the API, and the default scope list is{" "} <code>{"threads_basic"}</code> plus <code>{"threads_content_publish"}</code>. The client id and secret can be supplied as connect options by a machine caller, or read as the two credential fields.</p>
    <p>The start step answers an authorization action that a browser completes at the Threads authorization host, and the local CLI completes that OAuth callback itself, with <code>{"--redirect-uri"}</code> and a controlling terminal or with <code>{"--callback-url -"}</code>, as the <a href="/reference/credentials/#browser">credential reference</a> describes. That local callback path is fixture-tested against local servers only; no live Threads account was connected.</p>

    <h2 id="first-publish">First publish</h2>
    <p>The text that is sent is the target's <code>{"text"}</code> publish option:</p>
    <pre data-label="post.json"><code>{"{\n  \"type\": \"prepare\",\n  \"content\": {},\n  \"targets\": [\n    { \"provider\": \"threads\", \"options\": { \"text\": \"Hello from Syndroo.\" } }\n  ]\n}"}</code></pre>
    <pre data-label="terminal"><code>{"syndroo publish --input post.json --json"}</code></pre>
    <p>The provider pins <code>{"media_type"}</code> and <code>{"auto_publish_text"}</code> itself; they are not caller options. The only evidence-backed URL for an account is its profile URL, so a delivery reports the post id and, when the stored account has a username, the profile URL. No post permalink format is invented.</p>

    <h2 id="capabilities">Capabilities</h2>
    <p>The manifest declares <code>{"text"}</code>. <strong>UNRESOLVED.</strong> A text limit is not present in the reachable Meta artifacts, so this guide does not print one.</p>

    <h2 id="troubleshooting">Troubleshooting</h2>
    <p>The provider never retries and never reclassifies. A container that was created while the publish call failed would be a real ambiguous window; with the one-call path there is no stored container to reconcile, and a timeout after the call still stays{" "} <code>{"unknown"}</code> and non-retryable.</p>
    <p><strong>UNRESOLVED.</strong> The reachable Meta artifacts disagree on <code>.net</code>{" "} versus <code>.com</code> for both hosts, no general error-code table is available, and PKCE support is not documented in them. The provider uses the collection's <code>.net</code> pair by default for that reason.</p>

    <h2 id="revoke">Revoke and security</h2>
    <p><strong>UNRESOLVED.</strong> No token or app revocation procedure was retrieved from a primary Meta source, so this guide does not print one. Removing the app's access in your Meta account settings and then disconnecting the local connection is the safe local step:</p>
    <pre data-label="terminal"><code>{"syndroo connect --disconnect <connectionId>"}</code></pre>
