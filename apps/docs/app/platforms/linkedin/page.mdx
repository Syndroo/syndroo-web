        <h1 id="linkedin-setup">LinkedIn setup</h1>
        <p className="lede">LinkedIn publishing needs three values: an access token authorized for posting, the author to publish as, and an explicit API version. The adapter writes its own HTTP requests rather than using the restricted client SDK.</p>
        <div className="status-strip" aria-label="LinkedIn status recorded for 0.2.0-rc.1">
          <span className="status-chip"><span className="status-dot experimental"></span>Experimental</span>
          <span className="status-chip">Provider <code>{"linkedin-native"}</code></span>
        </div>

        <h2 id="status">Status and evidence</h2>
        <p>Syndroo <code>{"0.2.0-rc.1"}</code> is an unpublished release candidate: prepared in the repository, not published to npm, not tagged, and not deployed. LinkedIn is recorded as <strong>experimental</strong> for this candidate.</p>
        <p>Evidence: unit tests in the core repository, including workerd coverage. The review of the official JavaScript client found redistribution restrictions, so the adapter is an independent native HTTP implementation of the posts endpoint. There is no Mock SNS end-to-end coverage for LinkedIn, and no live-account acceptance record exists. See <a href="/concepts/#platform-readiness">Platform readiness</a> and the <a href="/#facts-source">capability record</a>.</p>

        <h2 id="prerequisites">What you need</h2>
        <ul>
          <li><strong>A LinkedIn member account</strong>, or an organization Page you administer, depending on what you intend to publish as.</li>
          <li><strong>A LinkedIn developer application</strong> with the API product access that allows posting.</li>
          <li><strong>The permission your target needs.</strong> The Posts API documents <code>{"w_member_social"}</code> for posting on behalf of an authenticated member, and <code>{"w_organization_social"}</code> for posting on behalf of an organization, where the authenticated member must hold a page role such as <code>{"ADMINISTRATOR"}</code>, <code>{"DIRECT_SPONSORED_CONTENT_POSTER"}</code>, or <code>{"CONTENT_ADMIN"}</code>. Product access and permission names are LinkedIn's to change, so confirm them on the current documentation.</li>
          <li><strong>A member access token</strong> from the OAuth flow LinkedIn documents. Syndroo does not run that flow and does not refresh tokens.</li>
          <li><strong>A running Worker and its API key.</strong> Either <a href="/operations/cloudflare/">a deployment in your own Cloudflare account</a> or <a href="/operations/local/">a local instance</a>. The Worker holds the platform credentials; clients hold only <code>{"SYNDROO_API_KEY"}</code>. If you have not set one up yet, the <a href="/quickstart/">first-post walkthrough</a> covers the whole path with Bluesky.</li>
        </ul>
        <p>The adapter reads three Worker secrets:</p>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">Secret</th><th scope="col">Required</th><th scope="col">Value</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row"><code>{"LINKEDIN_ACCESS_TOKEN"}</code></th><td>Yes</td><td>Access token authorized for posting as the author below.</td></tr>
              <tr><th scope="row"><code>{"LINKEDIN_AUTHOR"}</code></th><td>Yes</td><td>The publishing author as a URN: <code>{"urn:li:person:..."}</code> for a member, <code>{"urn:li:organization:..."}</code> for a Page. One author per deployment.</td></tr>
              <tr><th scope="row"><code>{"LINKEDIN_API_VERSION"}</code></th><td>Yes</td><td>An explicitly selected API version in <code>{"YYYYMM"}</code> form, such as <code>{"202601"}</code>. There is deliberately no default.</td></tr>
            </tbody>
          </table>
        </div>
        <p>The version and author are validated when the Worker reads them: a missing version, a malformed URN or an empty token leaves LinkedIn unconfigured, and selecting it returns HTTP <code>{"422"}</code> with <code>{"PLATFORM_NOT_CONFIGURED"}</code>.</p>

        <h2 id="credentials">Create the token and pick an author by hand</h2>
        <p>LinkedIn's developer portal, access programs and permission names change over time. Follow the official documentation linked under <a href="#sources">Official sources</a> while you work through this sequence.</p>
        <ol className="steps">
          <li>
            <h3 id="create-app">Create the developer application</h3>
            <p>Create an application in the LinkedIn developer portal and associate it with the Page that owns it.</p>
          </li>
          <li>
            <h3 id="request-access">Request the posting access you need</h3>
            <p>Ask for the API product that permits posting. Member posting and organization posting are separate permissions and may have separate approval requirements; organization posting generally also requires a role on the Page.</p>
          </li>
          <li>
            <h3 id="authorize">Complete the member authorization</h3>
            <p>Run LinkedIn's OAuth flow for the member who will act for the author, requesting the posting permission. This yields the access token you will store. Check who the token acts for, because the token and the author URN must belong together or the write fails with <code>{"errorCode"}</code> <code>{"AUTH"}</code>.</p>
          </li>
          <li>
            <h3 id="pick-version">Pick an explicit API version</h3>
            <p>Read the versioning documentation, choose a supported version and record it as <code>{"YYYYMM"}</code>. Syndroo sends exactly the version you set, so an unsupported or retired value fails at the platform instead of being silently upgraded.</p>
          </li>
        </ol>
        <div className="callout warn">
          <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" strokeWidth="2" strokeLinecap="round" aria-hidden="true"><path d="M12 9v4" /><path d="M12 17h.01" /><path d="M10.3 3.9 1.8 18a2 2 0 0 0 1.7 3h17a2 2 0 0 0 1.7-3L13.7 3.9a2 2 0 0 0-3.4 0Z" /></svg>
          <div>
            <span className="callout-title">Access is granted by LinkedIn, not by Syndroo.</span>
            <p>Product access, review and Page permissions are outside Syndroo's control. This page makes no promise about which program you qualify for, what it costs, or how long an approval takes.</p>
          </div>
        </div>

        <h2 id="configure">Add the secrets to the Worker</h2>
        <p>Put the values where your runtime reads secrets: Worker secrets for a deployment, <code>{".dev.vars"}</code> for a local instance. <a href="/operations/cloudflare/">Cloudflare deployment</a> and <a href="/operations/local/">Local development</a> cover the exact commands for each path.</p>
        <pre data-label="LinkedIn secrets"><code>{"LINKEDIN_ACCESS_TOKEN=\"your-linkedin-access-token\"\nLINKEDIN_AUTHOR=\"urn:li:person:your-member-id\"\nLINKEDIN_API_VERSION=\"202601\""}</code></pre>
        <div className="callout info">
          <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" strokeWidth="2" strokeLinecap="round" aria-hidden="true"><circle cx="12" cy="12" r="9" /><path d="M12 16v-5" /><path d="M12 8h.01" /></svg>
          <div>
            <span className="callout-title">Configuration is checked for shape, not for validity.</span>
            <p>Before accepting a post, Syndroo checks that all three values exist and are well formed. It does not call LinkedIn to test the token. An expired, revoked or under-permissioned token passes that check and surfaces later as a publication failure with <code>{"errorCode"}</code> <code>{"AUTH"}</code>.</p>
          </div>
        </div>

        <h2 id="first-post">Publish and check one post</h2>
        <p>The commands below publish for real once the secrets above are configured. Set the two client variables in the terminal that will call Syndroo.</p>
        <pre data-label="terminal"><code>{"export SYNDROO_URL=\"https://your-worker.your-subdomain.workers.dev\"\nexport SYNDROO_API_KEY=\"the-same-secret-your-worker-has\""}</code></pre>
        <div data-code-scope="publish">
          <pre data-label="POST /v1/posts"><code>{"curl -X POST \"$SYNDROO_URL/v1/posts\" \\\n  -H \"Authorization: Bearer $SYNDROO_API_KEY\" \\\n  -H \"Content-Type: application/json\" \\\n  -H \"Idempotency-Key: linkedin-setup-001\" \\\n  --data '{\n    \"content\": \"First post from my own Syndroo Worker.\",\n    \"platforms\": [\"linkedin\"]\n  }'"}</code></pre>
        </div>
        <p>The accepted response is HTTP <code>{"202"}</code> with status <code>{"queued"}</code>:</p>
        <pre data-label="202 Accepted"><code>{"{\n  \"id\": \"post_...\",\n  \"status\": \"queued\"\n}"}</code></pre>
        <p>HTTP <code>{"202"}</code> means the request was accepted for processing. It does not confirm that LinkedIn accepted anything, and it does not prove that the Queue has not already sent the platform request, because delivery can start immediately after acceptance. Read the stored state to learn the outcome:</p>
        <pre data-label="terminal"><code>{"curl \\\n  -H \"Authorization: Bearer $SYNDROO_API_KEY\" \\\n  \"$SYNDROO_URL/v1/posts/post_...\""}</code></pre>
        <pre data-label="200 OK"><code>{"{\n  \"id\": \"post_...\",\n  \"content\": \"First post from my own Syndroo Worker.\",\n  \"platforms\": [\"linkedin\"],\n  \"status\": \"published\",\n  \"publications\": [\n    {\n      \"platform\": \"linkedin\",\n      \"provider\": \"linkedin-native\",\n      \"status\": \"published\",\n      \"attempts\": 1,\n      \"externalId\": \"urn:li:share:7000000000000000000\",\n      \"errorAmbiguous\": false\n    }\n  ]\n}"}</code></pre>
        <p>A publication is stored as <code>{"published"}</code> only when LinkedIn confirms the created post. <code>{"queued"}</code> and <code>{"publishing"}</code> are not terminal; poll the same URL. Repeating the identical request with the same <code>{"Idempotency-Key"}</code> returns the stored result with HTTP <code>{"200"}</code> instead of creating a second post. See <a href="/api/#idempotency-header">Idempotency-Key</a>.</p>

        <h2 id="limits">Limits, tokens and external dependencies</h2>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">Item</th><th scope="col">Recorded for 0.2.0-rc.1</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row">Text limit</th><td>3,000 UTF-16 units after the adapter escapes reserved little-text characters, checked before the network call. Nothing is truncated; over-limit text fails with <code>{"INVALID_CONTENT"}</code>.</td></tr>
              <tr><th scope="row">Content type</th><td>Public text only. The comment text is escaped so reserved characters stay literal, and media, documents, mentions and audience targeting are outside this version.</td></tr>
              <tr><th scope="row">Credential maintenance</th><td>Yours. LinkedIn access tokens expire, and Syndroo neither refreshes nor renews them; obtain a new token and replace the Worker secret. LinkedIn documents a monthly API version cycle with scheduled retirements, so re-check the version you pin.</td></tr>
              <tr><th scope="row">External dependency</th><td>LinkedIn's product access, review process, terms and rate limits apply. Syndroo controls none of them, includes no pricing of its own, and promises nothing about a current plan, quota or approval outcome.</td></tr>
            </tbody>
          </table>
        </div>
        <p>Check the provider's current documentation before relying on a specific permission, version or limit. Those facts change on the provider's schedule, not on this page; the links under <a href="#sources">Official sources</a> are the references to re-check.</p>

        <h2 id="failures">When something fails</h2>
        <p>A failed publication stores <code>{"errorCode"}</code>, <code>{"errorMessage"}</code> and <code>{"errorAmbiguous"}</code> in the post response. Read them before you act.</p>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">What you see</th><th scope="col">What it means</th><th scope="col">What to do</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row">HTTP <code>{"422"}</code> <code>{"PLATFORM_NOT_CONFIGURED"}</code></th><td>A secret is missing, empty, or not in the required form: a malformed author URN or a version that is not <code>{"YYYYMM"}</code>.</td><td>Fix the secret named above, then send the request again. Nothing was stored or queued.</td></tr>
              <tr><th scope="row"><code>{"AUTH"}</code></th><td>LinkedIn rejected the token or the author: expired, revoked, missing the posting permission, or the token acts for a different member than the author URN.</td><td>Obtain a token with the right permission and author, update the secrets, and check the feed before resending.</td></tr>
              <tr><th scope="row"><code>{"INVALID_CONTENT"}</code></th><td>The escaped text exceeded the UTF-16 limit, or the content was not postable as plain text, and nothing was sent.</td><td>Shorten the text and publish again with a new key.</td></tr>
              <tr><th scope="row"><code>{"RATE_LIMIT"}</code></th><td>LinkedIn refused the request because of its own request limits.</td><td>Syndroo retries this automatically with backoff, up to three attempts. If it still fails, wait before trying again.</td></tr>
              <tr><th scope="row"><code>{"PROVIDER_UNAVAILABLE"}</code>, <code>{"NETWORK"}</code> or <code>{"UNKNOWN"}</code>, with <code>{"errorAmbiguous: true"}</code></th><td>The write may have reached LinkedIn; the outcome is unknown.</td><td>Check the feed and the author's activity by hand. Syndroo never resends an ambiguous publication automatically.</td></tr>
              <tr><th scope="row">Post status <code>{"partial"}</code></th><td>Some selected platforms succeeded and some failed.</td><td>Never resubmit the platforms that succeeded. The failed ones need attention only after you have excluded an ambiguous outcome.</td></tr>
            </tbody>
          </table>
        </div>
        <div className="callout warn">
          <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" strokeWidth="2" strokeLinecap="round" aria-hidden="true"><path d="M12 9v4" /><path d="M12 17h.01" /><path d="M10.3 3.9 1.8 18a2 2 0 0 0 1.7 3h17a2 2 0 0 0 1.7-3L13.7 3.9a2 2 0 0 0-3.4 0Z" /></svg>
          <div>
            <span className="callout-title">Rule out an ambiguous outcome before publishing again.</span>
            <p>If a publication is <code>{"failed"}</code> with <code>{"errorAmbiguous: true"}</code>, check the author's LinkedIn activity by hand first, because the post may already exist. Only when you have confirmed that nothing was published and you still want the post should you send a new request with a new <code>{"Idempotency-Key"}</code>. Reusing the old key replays the stored result instead of publishing. Read <a href="/concepts/#ambiguous-outcomes">Ambiguous outcomes</a> for the reasoning.</p>
          </div>
        </div>
