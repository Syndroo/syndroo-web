    <h1 id="devto">DEV.to</h1>

    <h2 id="overview">Overview</h2>
    <p>Provider id <code>{"devto"}</code>. DEV.to uses a personal API key sent in an{" "} <code>{"api-key"}</code> header, not an OAuth flow. An article is created with one call to{" "} <code>{"POST https://dev.to/api/articles"}</code>, and the article body is the explicit{" "} <code>{"body_markdown"}</code> option rather than the shared text.</p>

    <h2 id="requirements">Requirements</h2>
    <ul>
      <li>A DEV.to account and a personal API key for it.</li>
      <li>The title and the Markdown body you want to publish.</li>
    </ul>
    <p><strong>UNRESOLVED.</strong> The user-facing procedure for issuing or regenerating an API key was not confirmed on a primary documentation page, so this guide does not print a settings path.</p>

    <h2 id="credentials">Credentials</h2>
    <div className="table-wrap">
      <table>
        <thead>
          <tr>
            <th scope="col">Field</th>

            <th scope="col">Secret</th>
          </tr>

          <tr>
            <th scope="row"><code>{"apiKey"}</code></th>
            <td>The personal API key, sent in the <code>{"api-key"}</code> header.</td>
            <td>Yes</td>
          </tr>
        </tbody>
      </table>
    </div>
    <p>The key is validated by reading <code>{"GET /api/users/me"}</code>, which answers 200 with the user or 401 when the key is refused.</p>

    <h2 id="connect">Connect</h2>
    <pre data-label="terminal"><code>{"export SYNDROO_CREDENTIALS='{\"apiKey\":\"DEV_TO_API_KEY_PLACEHOLDER\"}'\nsyndroo connect devto --from-env --label writing"}</code></pre>
    <p>There are no connect options for this provider: the credential field is the whole connection input.</p>

    <h2 id="first-publish">First publish</h2>
    <p>An article target does not need the shared content, because the article carries its own title and body:</p>
    <pre data-label="post.json"><code>{"{\n  \"type\": \"prepare\",\n  \"content\": {},\n  \"targets\": [\n    {\n      \"provider\": \"devto\",\n      \"options\": {\n        \"title\": \"Publishing from the terminal\",\n        \"body_markdown\": \"# Hello\\n\\nSyndroo sends this article.\",\n        \"tags\": [\"devtools\"],\n        \"canonical_url\": \"https://example.com/posts/terminal\"\n      }\n    }\n  ]\n}"}</code></pre>
    <pre data-label="terminal"><code>{"syndroo publish --input post.json --json"}</code></pre>
    <p>The provider sends <code>{"published: true"}</code>; an unpublished draft is not the default of this target. A timeout after the article was created leaves the article id unknown to the client, so the outcome stays <code>{"unknown"}</code> and non-retryable.</p>

    <h2 id="capabilities">Capabilities</h2>
    <p>The manifest declares <code>{"article"}</code>. <strong>UNRESOLVED.</strong> The exact title maximum and the v1 rate limits are not stated on the retrieved API reference, so no number is printed here and the provider enforces none.</p>

    <h2 id="troubleshooting">Troubleshooting</h2>
    <p>A refused key is a 401, a validation failure is a 422 with an error string, and a rate limit is a 429. The provider never retries any of them, and no scope strings are invented: DEV.to documents no OAuth scopes for this key.</p>

    <h2 id="revoke">Revoke and security</h2>
    <p><strong>UNRESOLVED.</strong> The key regeneration and revocation procedure was not confirmed on the API reference, so this guide does not assert one. Regenerating or deleting the key in your DEV.to account settings, then disconnecting the local connection, is the safe local step:</p>
    <pre data-label="terminal"><code>{"syndroo connect --disconnect <connectionId>"}</code></pre>
