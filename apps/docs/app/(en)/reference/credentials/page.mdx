    <h1 id="credentials">Credentials</h1>
    <p className="lede">For the local workflow, a credential is read once, validated against the provider's schema and stored by Core. Later publishing never re-reads the environment variable or file you imported. The optional Server preview keeps deployment secrets in separate private state.</p>

    <h2 id="sources">Two explicit sources</h2>
    <ul>
    <li><code>{"--from-env"}</code> reads exactly <code>{"SYNDROO_CREDENTIALS"}</code>: one JSON object, at most 64 KiB.</li>
    <li><code>{"--credential-file"}</code> reads one private JSON file with the same object shape.</li>
    </ul>
    <p>Passing both, or passing neither when the provider needs credentials, is refused. An interactive run at a terminal offers the same two sources plus field-by-field entry, where a field the provider marks as secret is read with echo disabled. A non-interactive run never guesses and never blocks.</p>

    <h2 id="server">Server credentials</h2>
    <p><strong>Preview and unpublished.</strong> Server setup requires matching candidate <code>{"@syndroo/cli"}</code> and <code>{"@syndroo/cloudflare"}</code> packages; public npm installation is pending. The Server flow does not use the local <code>{"SYNDROO_CREDENTIALS"}</code> import described above.</p>
    <p><code>{"server connect threads"}</code> reads the App Secret through hidden terminal input, <code>{"THREADS_APP_SECRET"}</code> or <code>{"--app-secret-stdin"}</code>. Cloudflare authentication comes from the existing Wrangler login. The scoped CI bearer is stored privately or can be supplied through <code>{"--ci-token-stdin"}</code> when setup requests recovery.</p>
    <p>Never put the App Secret, CI bearer, Cloudflare admin bearer, <code>{"SECRET_KEY"}</code> or <code>{"RUNTIME_KEY"}</code> in a command argument, log, chat message or repository file. Deployment credentials can be imported together with <code>{"server deploy --yes --credentials-stdin"}</code> using protected input. See <a href="/getting-started/server/">Deploy a server</a> and the <a href="/reference/cli/#server">Server command reference</a>.</p>

    <h2 id="after">After a credential is stored</h2>
    <p>Core keeps the credential in the local credential store and records a reference on the connection; a plugin receives only what its own operation needs. Publishing does not depend on the environment variable or the import file still existing, so the file can be deleted once the connection works.</p>
    <p>A stored credential is released when the connection is disconnected. Disconnecting removes the local record only: Syndroo never revokes a platform credential, so revoke it at the platform as well. Each <a href="/platforms/">platform guide</a> says what is documented for its revocation.</p>

    <h2 id="browser">Local browser authorization</h2>
    <p>LinkedIn, Threads and Mastodon connect with an authorization action that a browser completes. The local CLI finishes that OAuth callback itself for all three. With <code>{"--redirect-uri"}</code> it binds exactly that loopback host, port and path in-process and consumes one redirect; the default is a pre-registerable loopback URI, and the bind needs a controlling terminal, so without one the run reports the pending action and exits 0. With <code>{"--callback-url -"}</code> it reads the redirected URL from standard input instead. A callback URL that carries <code>{"code"}</code> or <code>{"state"}</code> is refused on the command line as <code>{"CALLBACK_URL_INVALID"}</code>, because a secret must not reach the argument vector. This local callback path is verified by fixture tests against local HTTP servers only; no live LinkedIn, Threads or Mastodon account was connected.</p>
