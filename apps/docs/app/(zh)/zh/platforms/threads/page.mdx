    <h1 id="threads">Threads</h1>

    <h2 id="overview">概览</h2>
    <p>提供商 ID 为 <code>{"threads"}</code>。元数据记录了两步发布：先创建文本容器，再发布该容器。提供商采用文档中的单次调用路径，把 <code>{"media_type=TEXT"}</code> 与 <code>{"auto_publish_text=true"}</code> 一起发送，因此一次请求即可创建并发布文本帖子。</p>

    <h2 id="requirements">要求</h2>
    <ul>
      <li>一个配置了 Threads 用例的 Meta 应用，以及它的 client id 和 client secret。</li>
      <li>一个已注册、可供授权步骤回调的重定向 URI。</li>
      <li>一个已授权该应用的 Threads 账号。</li>
    </ul>

    <h2 id="credentials">凭证</h2>
    <div className="table-wrap">
      <table>
        <thead>
          <tr>
            <th scope="col">字段</th>
            <th scope="col">含义</th>
            <th scope="col">机密</th>
          </tr>
        </thead>
        <tbody>
          <tr>
            <th scope="row"><code>{"client_id"}</code></th>
            <td>应用的 client id。</td>
            <td>否</td>
          </tr>
          <tr>
            <th scope="row"><code>{"client_secret"}</code></th>
            <td>应用的 client secret。</td>
            <td>是</td>
          </tr>
        </tbody>
      </table>
    </div>
    <p>授权码会在 API 主机上交换，随后再按文档中的 60 天交换流程申请长期令牌。连接保存的是该令牌。</p>

    <h2 id="connect">连接</h2>
    <p><code>{"redirectUri"}</code> 必填；两个主机默认使用 Meta 公布的值，因此只提供一个主机的调用方不会在不知情的情况下混用主机对：</p>
    <pre data-label="connect.json"><code>{"{\n  \"type\": \"start\",\n  \"provider\": \"threads\",\n  \"options\": { \"redirectUri\": \"https://example.com/oauth/callback/threads\" }\n}"}</code></pre>
    <pre data-label="terminal"><code>{"syndroo connect --input connect.json --json"}</code></pre>
    <p>未提供选项时，授权主机为 <code>{"https://www.threads.net"}</code>，API 主机为 <code>{"https://graph.threads.net"}</code>，默认范围列表为 <code>{"threads_basic"}</code> 加 <code>{"threads_content_publish"}</code>。机器调用方可以把 client id 和 secret 作为连接选项传入，也可以把它们作为两个凭证字段读取。</p>
    <p>启动步骤会返回一个授权动作，由浏览器在 Threads 授权主机完成；本地 CLI 会自行完成该 OAuth 回调，使用 <code>{"--redirect-uri"}</code> 和控制终端，或使用 <code>{"--callback-url -"}</code>，如<a href="/zh/reference/credentials/#browser">凭证参考</a>所述。这条本地回调路径只针对本地服务器做了模拟测试；尚未连接真实的 Threads 账号。</p>

    <h2 id="server">部署服务器</h2>
    <p>本页的 <code>{"syndroo connect"}</code> 流程保持在本地。如需通过自己的 Cloudflare Worker 运行 Threads OAuth，并从 GitHub Actions 发布，请按照<a href="/zh/getting-started/server/">部署服务器</a>操作。该流程使用已确认的主机注册 <code>{"https://YOUR-WORKER.YOUR-SUBDOMAIN.workers.dev/oauth/callback/threads"}</code>，并运行 <code>{"syndroo server connect threads --app-id APP_ID"}</code>。</p>
    <p><strong>预览且未发布。</strong>Server 流程需要版本匹配的候选 <code>{"@syndroo/cli"}</code> 和 <code>{"@syndroo/cloudflare"}</code> 包；公共 npm 安装尚待提供。发布和验收限制见<a href="/zh/reference/cli/#server">CLI 参考</a>。</p>

    <h2 id="first-publish">首次发布</h2>
    <p>发送的文本来自目标的 <code>{"text"}</code> 发布选项：</p>
    <pre data-label="post.json"><code>{"{\n  \"type\": \"prepare\",\n  \"content\": {},\n  \"targets\": [\n    { \"provider\": \"threads\", \"options\": { \"text\": \"Hello from Syndroo.\" } }\n  ]\n}"}</code></pre>
    <pre data-label="terminal"><code>{"syndroo publish --input post.json --json"}</code></pre>
    <p>提供商会自行固定 <code>{"media_type"}</code> 和 <code>{"auto_publish_text"}</code>；它们不是调用方选项。账号唯一有证据支持的 URL 是个人资料 URL，因此投递结果会报告帖子 ID，并且当已保存的账号有用户名时，还会报告个人资料 URL。本指南不虚构帖子永久链接格式。</p>

    <h2 id="capabilities">能力</h2>
    <p>清单声明 <code>{"text"}</code>。<strong>未解决。</strong>可获取的 Meta 资料中没有文本长度限制，因此本指南不给出具体数字。</p>

    <h2 id="troubleshooting">故障排除</h2>
    <p>提供商从不重试，也不会重新分类。如果在发布调用失败时已经创建容器，就会形成真实的不确定窗口；使用单次调用路径时没有需要核对的已保存容器，调用后的超时仍保持 <code>{"unknown"}</code> 且不可重试。</p>
    <p><strong>未解决。</strong>可获取的 Meta 资料对两个主机应为 <code>.net</code> 还是 <code>.com</code> 存在分歧，也没有通用错误代码表，并且这些资料没有记录 PKCE 支持。因此提供商默认使用该集合中的 <code>.net</code> 主机对。</p>

    <h2 id="revoke">撤销与安全</h2>
    <p><strong>未解决。</strong>尚未从 Meta 的一手来源获取令牌或应用撤销步骤，因此本指南不提供具体做法。安全的本地步骤是在 Meta 账号设置中移除应用访问权限，然后断开本地连接：</p>
    <pre data-label="terminal"><code>{"syndroo connect --disconnect <connectionId>"}</code></pre>
