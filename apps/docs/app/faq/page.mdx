        <h1 id="faq">FAQ</h1>
        <p className="lede">Seven situations worth knowing before you publish.</p>

        <h2 id="configuration">Configuration still fails</h2>
        <p>Run <code>{"syndroo doctor --local"}</code>: it names the failing check and sends nothing. When the failing check is a credential, confirm the whole exported group is present in this shell and re-connect the account as described in <a href="/accounts/">Account configuration</a>. <code>{"connect"}</code> defaults to local mode; the older <code>{"auth set"}</code> command still requires <code>{"--local"}</code>. A credential file must be a regular file you own, mode <code>{"600"}</code>, not a symlink, and no larger than 64 KiB. Hidden terminal entry needs <code>{"--save-credential-file <new-path>"}</code> preselected; the CLI never guesses a path.</p>

        <h2 id="state-upgrade">State format 2</h2>
        <p>New local installs start at state format 2. If an existing state is still format 1, stop every other Syndroo writer and upgrade explicitly before publishing records that need format 2:</p>
        <pre data-label="terminal"><code>{"syndroo state upgrade --to 2 --confirm-no-writers --yes --no-input"}</code></pre>
        <p>Publishing and dry runs never upgrade state. An older CLI refuses format 2 state, and an interrupted upgrade resumes only through the same command.</p>

        <h2 id="changed-source">I edited the file after confirming</h2>
        <p>Within one invocation, an edit made while or after confirming cannot change what is sent: publishing reads the file once and uses that same parsed snapshot. A separate publish after a dry run reads the current file, so edits between those commands do change its input. Check the receipt before considering any new post; changing a key is not a repair for a failed or unknown result.</p>

        <h2 id="duplicate-key">The same key again</h2>
        <p>A <code>{"key"}</code> is the identity of one post. Repeating a publish with the same key and the same content does not create a second copy, and the same key with different content is refused instead of sent again. A target that already succeeded is never republished.</p>

        <h2 id="unknown-result">The result is unknown</h2>
        <p>An <code>{"unknown"}</code> target may have reached the platform. Read the receipt, inspect the platform account by hand and stop: an unknown target stays blocked, and neither an automatic nor a deliberate retry may resend that content blindly.</p>

        <h2 id="state-recovery">Recover the local state</h2>
        <p>Stop every other Syndroo process first, then inspect and recover:</p>
        <pre data-label="terminal"><code>{"syndroo state inspect\nsyndroo state recover --confirm-no-writers --yes"}</code></pre>
        <p>If the state holds a lock with no readable owner, stop and diagnose it by hand instead of deleting the state directory.</p>

        <h2 id="limits">What this candidate does not do</h2>
        <p>The <code>{"0.7.0-rc.1"}</code> candidate publishes plain text to Bluesky, Threads, LinkedIn personal accounts, and Mastodon public statuses, plus public personal articles to DEV.to. It has no media upload, scheduler, daemon, automatic refresh, or telemetry, and a local failure never uses a server fallback. Local state can hold post content and account metadata; <code>{"0700"}</code> and <code>{"0600"}</code> permissions are not encryption. No live account was connected and no real post was published for this candidate; fixture tests are not live-account acceptance. The full packaged-platform locality gate, full Linux publishing, and the complete macOS/Linux Node.js matrix remain unverified.</p>
