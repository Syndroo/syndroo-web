        <h1 id="agent-setup">Drive publishing from an agent</h1>
        <p className="lede">The CLI ships the Syndroo Skill, which describes the same direct flow for an agent: build the document in memory, publish it with <code>{"--data"}</code>, and report every target. The agent needs command execution on this device and explicit authorization for the exact content and accounts.</p>

        <h2 id="load-the-skill">Load the Skill</h2>
        <p>Install the CLI and connect accounts first, using <a href="/">Quick start</a> and <a href="/accounts/">Account configuration</a>; each platform named in <code>{"platforms"}</code> needs its own active binding. The local path has no Syndroo server in the loop, so the agent runs <code>{"syndroo"}</code> on the machine that holds the local state and account bindings.</p>
        <p>Point a Skill-capable client at the bundled directory, which holds <code>{"SKILL.md"}</code> and its references:</p>
        <pre data-label="terminal"><code>{"syndroo skill path"}</code></pre>
        <p>The Skill is guidance. It is not an installer and does not prove that any particular agent client will discover or run it.</p>

        <h2 id="the-flow">The flow</h2>
        <pre data-label="terminal"><code>{"syndroo doctor --local\nsyndroo auth status --local\n\nsyndroo publish --data '{\"key\":\"hello-001\",\"content\":\"Hello\",\"platforms\":[\"bluesky\"]}' --yes --no-input --json\nsyndroo receipts show <operation-id> --json"}</code></pre>
        <p><code>{"doctor --local"}</code> and <code>{"auth status --local"}</code> read only; the status command stays offline unless you add <code>{"--verify"}</code>. If an account is not bound yet, use <code>{"syndroo connect"}</code> as described in <a href="/accounts/">Account configuration</a>; do not invent a credential source for the agent.</p>

        <h2 id="steps">Steps the agent takes</h2>
        <ol className="steps">
          <li>
            <h3 id="read-the-skill">Read the Skill</h3>
            <p>Open the directory <code>{"syndroo skill path"}</code> prints and follow its workflow.</p>
          </li>
          <li>
            <h3 id="request-approval">Request approval of the text and the account</h3>
            <p>Confirm that the user authorized this exact text, these target accounts, and this action. If the user&apos;s existing specific authorization already covers them, proceed without another conversation turn. <code>{"--yes"}</code> skips the interactive prompt for that run; it is not authorization, and the agent must not change the content after approval.</p>
          </li>
          <li>
            <h3 id="execute-and-report">Execute and report</h3>
            <p>Publish the approved document, then report the operation id and one honest outcome per target.</p>
          </li>
        </ol>
        <p>Keep credentials out of prompts, chat, and command arguments: <code>{"--data"}</code> carries content only. Credentials belong to the environment variables or owner-only files described in <a href="/accounts/">Account configuration</a>. Inspect the platform by hand when a target comes back <code>{"unknown"}</code>, and never resend that content blindly.</p>
        <p>Generate strict JSON with a serializer and pass it as one argument, rather than interpolating post text into shell syntax. No temporary file is required. Inline JSON can appear in shell history and process arguments; use <code>{"--input -"}</code> for sensitive text, or <code>{"--input post.json"}</code> for a maintained file. Choose one input source.</p>
        <p>Add <code>{"--dry-run"}</code> when inspection is useful. It writes no state, resolves no credentials, and makes no network calls. A later publish reads its current input; within a single invocation, confirmation and sending use the same parsed snapshot.</p>
        <p>The local candidate has no scheduler, daemon, media upload, automatic refresh, or telemetry, and no live account was connected for this release. Do not claim a verified publish from fixture tests.</p>
