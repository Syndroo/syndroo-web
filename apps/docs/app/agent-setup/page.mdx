        <h2 id="workflow">The manual HTTP workflow</h2>
        <ol className="steps">
          <li>
            <h3 id="prove-the-service">Prove the service answers</h3>
            <p>Health needs no authentication, so check it before involving any credential. Set the URL first:</p>
            <pre data-label="terminal"><code>{"export SYNDROO_URL=\"https://your-worker.your-subdomain.workers.dev\"\ncurl \"$SYNDROO_URL/health\""}</code></pre>
            <p>Expected: <code>{"{\"status\":\"ok\"}"}</code>. This endpoint always answers <code>{"200"}</code> while the Worker is running, including in maintenance mode. Maintenance mode only rejects new posts: <code>{"POST /v1/posts"}</code> then returns <code>{"503"}</code> with <code>{"SERVICE_UNAVAILABLE"}</code>, and reads keep working.</p>
          </li>
          <li>
            <h3 id="give-the-agent-a-key">Give the client the credential out of band</h3>
            <p>Put <code>{"SYNDROO_API_KEY"}</code> in the environment or secret store the agent process reads. Do not paste the key into a prompt, a chat transcript, an issue, a screenshot or a log line. The key can publish, so it deserves the same handling as a password.</p>
            <pre data-label="terminal"><code>{"export SYNDROO_URL=\"https://your-worker.your-subdomain.workers.dev\"\nexport SYNDROO_API_KEY=\"the-secret-your-worker-has\""}</code></pre>
          </li>
          <li>
            <h3 id="draft-in-the-client">Draft and preview in the client</h3>
            <p>Let the agent write the text and show it to you, per platform. Two things are worth stating plainly: the draft is produced by your agent, not by Syndroo, and the preview is a client feature. The API has no preview or approval endpoint, and it accepts whatever a confirmed request contains.</p>
            <p>Keep each platform's own limit in view while drafting: the candidate enforces 300 Unicode code points and 3,000 UTF-8 bytes for Bluesky, 500 characters for Threads, 280 weighted characters for X, 4,096 code points for Tumblr, and at most 3,000 UTF-16 units after escaping for LinkedIn. Each <a href="/platforms/bluesky/">platform guide</a> records its own limit and its own counting rule.</p>
          </li>
          <li>
            <h3 id="confirm-before-sending">Confirm before anything is sent</h3>
            <p>A person approves the text. This is a workflow rule for your client, not a service feature. It is the only thing standing between a model's suggestion and a public post.</p>
          </li>
          <li>
            <h3 id="send-one-request">Send one request with a stable key</h3>
            <p>Use one <code>{"Idempotency-Key"}</code> per logical post, derived from content the client can reproduce (a release tag, a commit SHA, a job id). The same key with the same body returns the original result; the same key with different text is rejected with <code>{"409"}</code>.</p>
            <div data-code-scope="publish">
              <pre data-label="POST /v1/posts"><code>{"curl -X POST \"$SYNDROO_URL/v1/posts\" \\\n  -H \"Authorization: Bearer $SYNDROO_API_KEY\" \\\n  -H \"Content-Type: application/json\" \\\n  -H \"Idempotency-Key: agent-run-2291\" \\\n  --data '{\n    \"content\": \"Nightly ingest finished: 41,208 rows reconciled, 0 quarantined records.\",\n    \"platforms\": [\"bluesky\", \"threads\"]\n  }'"}</code></pre>
            </div>
          </li>
          <li>
            <h3 id="treat-202-as-accepted">Treat HTTP 202 as accepted, not published</h3>
            <p>The reply is <code>{"{\"id\": \"post_...\", \"status\": \"queued\"}"}</code> (or <code>{"\"scheduled\""}</code>). HTTP <code>{"202"}</code> does not confirm platform success, and it describes the state when the Worker accepted the request: by the time the response reaches you, a fast Queue consumer may already have published the post. Only the post's own status tells you what happened, so poll it until it is terminal.</p>
            <pre data-label="terminal"><code>{"curl -H \"Authorization: Bearer $SYNDROO_API_KEY\" \\\n  \"$SYNDROO_URL/v1/posts/post_...\""}</code></pre>
            <p>Terminal post statuses are <code>{"published"}</code>, <code>{"partial"}</code> and <code>{"failed"}</code>. While a post is <code>{"queued"}</code> or <code>{"publishing"}</code>, wait and ask again instead of sending a new request.</p>
          </li>
          <li>
            <h3 id="read-failures">Read failures per platform</h3>
            <p>Each publication entry carries <code>{"status"}</code>, <code>{"attempts"}</code>, <code>{"errorCode"}</code>, <code>{"errorMessage"}</code>, <code>{"errorAmbiguous"}</code>, and the identifiers the platform returned. <code>{"errorAmbiguous: true"}</code> means the write may have reached the platform: stop, check by hand, and never resend automatically.</p>
          </li>
        </ol>

        <h2 id="example-instruction">An instruction block you can adapt</h2>
        <p>This is a starting point for your own agent's instructions. It encodes the guardrails above; adjust the platform list and the tone, and keep the safety rules.</p>
        <pre data-label="agent instructions (adapt freely)"><code>{"You publish social posts through a self-hosted Syndroo Worker.\n\nEndpoint: $SYNDROO_URL (set in my environment; do not print it)\nAuth: send the header \"Authorization: Bearer $SYNDROO_API_KEY\" (also from my environment)\n\nRules:\n1. Never publish without showing me the exact text per platform and getting my yes.\n2. One logical post, one Idempotency-Key. Reuse the key only when retrying the identical body.\n3. Treat HTTP 202 as \"accepted\", never as \"published\". Confirm with\n   GET /v1/posts/{id} until the status is published, partial or failed.\n4. If a publication has errorAmbiguous true, tell me to check the platform by hand.\n   Do not resend it, and do not send a new key for the same text.\n5. If one platform fails and others published, retry nothing on my behalf; report per platform.\n6. Never put the API key, or any platform token, in a prompt, a log, a commit or an issue."}</code></pre>

        <h2 id="credentials">Credential and secret handling</h2>
        <ul>
          <li><strong><code>{"SYNDROO_API_KEY"}</code> is a publishing credential.</strong> It is not a read-only key. Treat anyone who has it as able to publish through your Worker.</li>
          <li><strong>Platform credentials stay in the Worker.</strong> Bluesky, Threads, X, Tumblr and LinkedIn secrets are configured on your deployment; clients never hold them.</li>
          <li><strong>The client holds one secret.</strong> The agent process needs the Syndroo URL and the API key, and nothing else.</li>
          <li><strong>Rotation is replacing a secret.</strong> Change the value on the Worker, then update the environment your client reads. There is no token-issuing flow in this candidate.</li>
          <li><strong>Nothing is sent to Syndroo by the website.</strong> The marketing demo is simulated and performs no request.</li>
        </ul>

        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">Response</th><th scope="col">Meaning</th><th scope="col">Correct client behaviour</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row"><code>{"202"}</code> with <code>{"status: queued"}</code></th><td>Accepted; one pending publication per platform was stored.</td><td>Keep the returned id and poll it.</td></tr>
              <tr><th scope="row"><code>{"200"}</code> with <code>{"replayed: true"}</code></th><td>The same key and the same body were sent again.</td><td>Use the returned post; do not publish another.</td></tr>
              <tr><th scope="row"><code>{"409"}</code> <code>{"IDEMPOTENCY_CONFLICT"}</code></th><td>The key already belongs to a different request.</td><td>Do not retry with the same key. Use a new key only if the post is genuinely new.</td></tr>
              <tr><th scope="row"><code>{"401"}</code> <code>{"UNAUTHORIZED"}</code></th><td>The Bearer token is missing or wrong.</td><td>Fix the credential. Do not retry in a loop.</td></tr>
              <tr><th scope="row"><code>{"422"}</code> <code>{"PLATFORM_NOT_CONFIGURED"}</code></th><td>That platform is not installed or its credentials are missing.</td><td>Configure the platform, or drop it from <code>{"platforms"}</code>.</td></tr>
              <tr><th scope="row"><code>{"partial"}</code> post status</th><td>At least one platform published and at least one did not.</td><td>Act per publication. Never resend the platforms that already published.</td></tr>
              <tr><th scope="row"><code>{"failed"}</code> with <code>{"errorAmbiguous: true"}</code></th><td>The write may have succeeded remotely.</td><td>Verify by hand before any further publishing.</td></tr>
            </tbody>
