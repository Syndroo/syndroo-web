        <h1 id="publishing">Publish and retry</h1>
        <p className="lede">One logical post moves through one publish command: the CLI parses the document, validates it, sends that same parsed text to every target and records one receipt per target. A preview is available before you commit, not a required first phase.</p>

        <h2 id="document">The document</h2>
        <pre data-label="post.json"><code>{"{\n  \"schemaVersion\": 1,\n  \"key\": \"release-announcement-001\",\n  \"content\": \"Syndroo now publishes from the command line.\",\n  \"platforms\": [\"bluesky\", \"threads\", \"linkedin\"],\n  \"overrides\": { \"bluesky\": { \"content\": \"Shorter version for Bluesky.\" } }\n}"}</code></pre>
        <p><code>{"key"}</code> is the stable identity of this post for its whole life (1-128 characters from <code>{"A-Z a-z 0-9 . _ : -"}</code>). <code>{"content"}</code> is non-blank text of at most 10000 Unicode code points, <code>{"platforms"}</code> is a non-empty list naming only <code>{"bluesky"}</code>, <code>{"threads"}</code> or <code>{"linkedin"}</code>, and <code>{"overrides"}</code> may only name a selected platform. <code>{"schemaVersion"}</code> is optional and defaults to <code>{"1"}</code>. The file is strict JSON, limited to 64 KiB before decoding, and <code>{"--input -"}</code> reads stdin.</p>
        <p>A document may arrive as a file, as <code>{"--data '<json>'"}</code> or on stdin, but only one input source per run: combining them is a usage error that fails before anything is read, sent or written.</p>

        <h2 id="preview">Preview</h2>
        <p>A preview is optional and read-only: it parses and validates the document using existing local config and account bindings, but takes no write lock, resolves no credentials and makes no network request. It creates no state. Read the printed text and target account before continuing.</p>
        <pre data-label="terminal"><code>{"syndroo publish --input post.json --dry-run --json"}</code></pre>
        <p>A later publish reads the current input, not a saved preview. Editing the file between these two commands changes what the later publish sends. Keep the input unchanged if you intend to publish what you previewed.</p>

        <h2 id="publish">Publish</h2>
        <p>The CLI reads the file once, validates it, and sends exactly that parsed text, so editing <code>{"post.json"}</code> after the confirmation cannot change what is published. Execution sends at most one content request per target. When nobody can answer a prompt, the run needs both <code>{"--yes"}</code> and <code>{"--no-input"}</code>: <code>{"--yes"}</code> only skips the prompt, it is not an authorization. A missing confirmation exits <code>{"2"}</code> and sends nothing.</p>
        <pre data-label="terminal"><code>{"syndroo publish --input post.json --yes --no-input --json"}</code></pre>
        <p>For generated content, pass serialized JSON as one argument with <code>{"--data"}</code>; a temporary file is not required. Inline content can appear in shell history and process arguments. Use <code>{"--input -"}</code> for sensitive text, and keep credentials out of every post document.</p>

        <h2 id="receipts">Receipts</h2>
        <pre data-label="terminal"><code>{"syndroo receipts list --limit 20\nsyndroo receipts show <result.operationId> --json"}</code></pre>
        <p>Each target reports <code>{"status"}</code>, <code>{"reused"}</code>, <code>{"attempts"}</code>, <code>{"remoteId"}</code>, <code>{"url"}</code>, <code>{"writeDisposition"}</code> and a <code>{"retry"}</code> verdict; the aggregate is <code>{"succeeded"}</code>, <code>{"partial"}</code>, <code>{"failed"}</code>, <code>{"unknown"}</code> or <code>{"blocked"}</code>. A <code>{"null"}</code> url means no verified link is known, so do not build one.</p>

        <h2 id="unknown-and-retry">Unknown results and retry</h2>
        <p>Retry is explicit and direct: it names the safe targets to try again. Only targets whose failure is provably <code>{"not_applied"}</code> are eligible, and only within three content attempts per logical delivery. A selection that includes an <code>{"unknown"}</code> target blocks the whole retry, so narrow it to other safe targets instead. A succeeded target is never republished.</p>
        <pre data-label="terminal"><code>{"syndroo retry <operation-id> --to threads --yes --no-input --json\nsyndroo retry <operation-id> --to threads --dry-run --json"}</code></pre>
        <p>The second command is an optional read-only preview, not a required step. Retry windows must have passed; rotating credentials requires re-verifying the same stable account.</p>
        <p><code>{"unknown"}</code> means the write may have reached the platform. Read the receipt, inspect the account by hand and stop; do not resend that content, and do not treat an unknown target as retryable.</p>
