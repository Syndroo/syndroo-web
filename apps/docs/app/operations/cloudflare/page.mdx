        <h2 id="steps">Steps</h2>
        <ol className="steps">
          <li>
            <h3 id="deploy">Deploy from the repository</h3>
            <p>Follow the deploy section of the product README: <a href="https://github.com/Syndroo/syndroo/blob/main/README.md">Syndroo README (deploy procedure)</a>. It links a <strong>Deploy to Cloudflare</strong> button, whose documented behaviour is to create an independent repository in your account, ask for <code>{"SYNDROO_API_KEY"}</code>, provision the D1 database and Queue, apply the migrations, configure the Cron Trigger, and deploy the Worker.</p>
            <p>Two limits are recorded for this candidate: the button still deploys <em>this source repository</em>, and the thin deployment template passed isolated local installation, migration, build and startup checks but is not wired to the button and is not published to a registry. There is no <code>{"npm install syndroo"}</code> path in this candidate.</p>
          </li>
          <li>
            <h3 id="api-key">Choose the API key at deploy time</h3>
            <p><code>{"SYNDROO_API_KEY"}</code> is a long random secret that you invent. It is the Bearer token every client sends, and it can publish. Store it in your own secret manager as well; the Worker cannot show it back to you.</p>
          </li>
          <li>
            <h3 id="platform-secrets">Add platform secrets after the deployment</h3>
            <p>Open the deployed Worker, then <strong>{"Settings → Variables and Secrets"}</strong>, and add only the credentials for the platforms you intend to publish to. Each <a href="/platforms/bluesky/">platform guide</a> lists the exact names and what the platform requires.</p>
            <ul>
              <li>Platforms are enabled independently; a platform without credentials returns HTTP <code>{"422"}</code> and <code>{"PLATFORM_NOT_CONFIGURED"}</code>.</li>
              <li>A deployment with no platform credentials can still answer health checks, but it cannot accept posts.</li>
              <li>Keep platform secrets out of any template's required-secret list; they are optional per deployment.</li>
            </ul>
          </li>
          <li>
            <h3 id="verify">Verify the deployment</h3>
            <pre data-label="terminal"><code>{"curl \"https://your-worker.your-subdomain.workers.dev/health\"\n# {\"status\":\"ok\"}"}</code></pre>
            <p>Then publish one post to one platform, exactly as in <a href="/quickstart/">Publish your first post</a>. If the API key is missing or wrong, the request fails with HTTP <code>{"401"}</code>; if a platform is not configured, it fails with <code>{"422"}</code> before anything is stored.</p>
          </li>
        </ol>

        <h2 id="boundaries">Boundaries and cautions</h2>
        <ul>
          <li><strong>Never deploy using the local Wrangler environment.</strong> Local runs read <code>{".dev.vars"}</code> and a local database; production reads Worker secrets.</li>
          <li><strong>No dashboard.</strong> Everything after deployment goes through the HTTP API, <code>{"wrangler"}</code> or the Cloudflare dashboard's own secret and log views.</li>
          <li><strong>Migrations are part of deployment.</strong> Local development applies migrations to a local database; that does not migrate production.</li>
          <li><strong>You maintain the credentials.</strong> Renew, rotate and revoke each platform credential according to that provider's own rules, and replace the Worker secret when you do. Syndroo has no automatic token refresh.</li>
          <li><strong>Scheduling has a scan cadence, not a completion guarantee.</strong> Cron looks for due posts every 15 minutes, then queue and platform time are added on top. The requested <code>{"scheduledAt"}</code> is the earliest intended time, and no upper bound is promised.</li>
        </ul>
