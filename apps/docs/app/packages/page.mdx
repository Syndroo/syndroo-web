        <h3 id="service-package">The service package</h3>
        <p><code>{"@syndroo/cloudflare-worker"}</code> is what an instance runs: a Bearer-authenticated HTTP API in front of D1, a Queue producer and consumer, and a Cron Trigger. It also carries the D1 migration history and the <code>{"syndroo-deploy"}</code> command that repairs a missing database binding, applies remote migrations and deploys the Worker.</p>
        <p>Deploying it is the <a href="/operations/cloudflare/">Cloudflare deployment</a> path; running it on your machine is <a href="/operations/local/">Local development</a>. Both answer the same question, which is how you get an instance. Nothing else on this site can be used before that question is answered.</p>

        <h3 id="client-library">The client library</h3>
        <p><code>{"@syndroo/sdk"}</code> is a thin TypeScript client over the documented <code>{"/v1"}</code> contract. It wraps health, create, read, list and a bounded poll for a terminal status, and it adds no server behaviour. It performs exactly one HTTP request per call and never retries a write.</p>
        <p>It has no runtime dependencies: it uses the runtime's global <code>{"fetch"}</code>, <code>{"AbortSignal"}</code> and Web Streams. An API key belongs in a trusted environment, never in a browser bundle or a <code>{"NEXT_PUBLIC_*"}</code> variable.</p>

        <h3 id="terminal-command">The terminal command</h3>
        <p><code>{"@syndroo/cli"}</code> installs the <code>{"syndroo"}</code> command. It owns argument parsing, the post document, the preview and the exit codes, and it defers authentication, retries and polling to the SDK. Its tarball also carries the official Syndroo Skill in <code>{"skills/syndroo"}</code>, so an agent that can run a shell gets the workflow and the command from one install.</p>
        <p>The command path is <code>{"Skill -> CLI -> SDK -> HTTP API -> Worker"}</code>. Direct HTTP remains the fallback for a client that cannot run the CLI; it is not a second attempt after a CLI failure.</p>

        <h2 id="installing-a-candidate">Installing a candidate</h2>
        <p>Because nothing is published, the package you install is a tarball you build yourself from the product repository. This is the same artifact npm would receive later, so the code you exercise is the code that will ship.</p>
        <pre data-label="terminal"><code>{"git clone https://github.com/Syndroo/syndroo\ncd syndroo\nnpm ci\nnpm run build\nmkdir -p /tmp/syndroo-pack\nnpm pack --workspace @syndroo/sdk --pack-destination /tmp/syndroo-pack\nnpm pack --workspace @syndroo/cli --pack-destination /tmp/syndroo-pack"}</code></pre>
        <p>That leaves two files in <code>{"/tmp/syndroo-pack"}</code>: <code>{"syndroo-sdk-0.4.0-rc.1.tgz"}</code> and <code>{"syndroo-cli-0.4.0-rc.1.tgz"}</code>. Install the SDK first, then the CLI:</p>
        <pre data-label="terminal"><code>{"mkdir syndroo-quickstart\ncd syndroo-quickstart\nnpm init -y\nnpm install /tmp/syndroo-pack/syndroo-sdk-0.4.0-rc.1.tgz\nnpm install /tmp/syndroo-pack/syndroo-cli-0.4.0-rc.1.tgz"}</code></pre>
        <div className="callout info">
          <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" strokeWidth="2" strokeLinecap="round" aria-hidden="true"><circle cx="12" cy="12" r="9" /><path d="M12 16v-5" /><path d="M12 8h.01" /></svg>
          <div>
            <span className="callout-title">Order matters.</span>
            <p>The CLI declares <code>{"@syndroo/sdk"}</code> as its only dependency, pinned to an exact version. Installing the SDK first means the second command finds that version already present; installing the CLI on its own makes the installer look on the registry for a version that is not there yet, and it fails.</p>
          </div>
        </div>
        <p>If you only need the client library, the SDK tarball installs on its own: <code>{"npm install /tmp/syndroo-pack/syndroo-sdk-0.4.0-rc.1.tgz"}</code>.</p>

        <h2 id="not-published">What is not published yet</h2>
        <ul>
          <li>None of the three packages has a registry entry, a dist-tag or a GitHub Release for these candidates.</li>
          <li>Installing by package name from a registry is a release step that has not happened. Until it does, every install instruction on this site names a file, not a package name.</li>
          <li>Because a version cannot be republished, a problem found after publication is fixed with a new release candidate or a patch version rather than by replacing the existing artifact.</li>
          <li>The packages are candidates, so the version numbers above can change before a stable release, and a changed number means new tarballs.</li>
        </ul>
        <p>Platform status is unaffected by packaging. Bluesky and Threads are mock-tested, and X, Tumblr and LinkedIn are experimental. A configured instance is a separate fact from a validated platform; see <a href="/#platform-status">Platform status</a>.</p>
