        <h1 id="sdk-quickstart">Publish your first post from your own code</h1>
        <p className="lede">The SDK is a thin TypeScript client for one deployed instance. This path installs the candidate tarball, creates a single post under a stable idempotency key, and reads the per-platform result back. It ends with one published post on one platform.</p>

The instance it calls is a <code>{"@syndroo/cloudflare-worker"}</code> candidate at <code>{"0.2.0-rc.1"}</code>. Once the platform credentials are configured in that instance, the code below publishes for real.</p>

        <h2 id="before-you-start">Before you start</h2>
        <ul>
          <li><strong>Node.js 22 or newer.</strong> The SDK has no runtime dependencies; it uses the runtime's global <code>{"fetch"}</code>, <code>{"AbortSignal"}</code> and Web Streams, so there is nothing to polyfill and nothing else to install.</li>
          <li><strong>A running instance.</strong> Deploy the Worker with <a href="/operations/cloudflare/">Cloudflare deployment</a>, or run it locally with <a href="/operations/local/">Local development</a>. Both end with a URL and an API key.</li>
          <li><strong>One platform's credentials, configured in the instance.</strong> This page uses Bluesky; the <a href="/platforms/bluesky/">Bluesky guide</a> lists the secret names.</li>
          <li><strong>A trusted environment for the API key.</strong> The key can publish. Keep it in a server process, a CI credential store or a CLI environment, never in a static page, a browser bundle or a <code>{"NEXT_PUBLIC_*"}</code> variable.</li>
        </ul>

        <h2 id="install">Install the candidate</h2>
        <p>Build the tarball in a checkout, then install that file into your project. No registry access is involved.</p>
        <pre data-label="terminal"><code>{"git clone https://github.com/Syndroo/syndroo\ncd syndroo\nnpm ci\nnpm run build\nnpm pack --workspace @syndroo/sdk --pack-destination /tmp/syndroo-pack"}</code></pre>
        <pre data-label="terminal"><code>{"mkdir syndroo-sdk-app\ncd syndroo-sdk-app\nnpm init -y\nnpm install /tmp/syndroo-pack/syndroo-sdk-0.4.0-rc.1.tgz"}</code></pre>
        <p>The CLI and the agent paths install the same SDK tarball, because the CLI depends on it. If you also want a terminal command, <a href="/quickstart/cli/">the CLI quickstart</a> installs both files together.</p>

        <h2 id="first-post">Create one post</h2>
        <p>Point the client at your instance and read the configuration from the environment. The constructor checks its own arguments before any request is made, and throws <code>{"SyndrooConfigError"}</code> when they cannot work.</p>
        <pre data-label="publish.mjs"><code>{"import { SyndrooClient } from \"@syndroo/sdk\";\n\nconst syndroo = new SyndrooClient({\n  baseUrl: process.env.SYNDROO_BASE_URL,\n  apiKey: process.env.SYNDROO_API_KEY,\n});\n\n// One logical post, one key. The key is what makes a retry safe.\nconst receipt = await syndroo.posts.create(\n  {\n    content: \"First post through my own Syndroo instance.\",\n    platforms: [\"bluesky\"],\n  },\n  { idempotencyKey: \"first-post-001\" },\n);\n\nconsole.log(\"accepted:\", receipt.id, receipt.status);"}</code></pre>
        <p>Set the two variables and run it:</p>
        <pre data-label="terminal"><code>{"export SYNDROO_BASE_URL=\"https://your-worker.your-subdomain.workers.dev\"\nexport SYNDROO_API_KEY=\"the-same-secret-your-worker-has\"\nnode publish.mjs"}</code></pre>
        <div className="callout info">
          <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" strokeWidth="2" strokeLinecap="round" aria-hidden="true"><circle cx="12" cy="12" r="9" /><path d="M12 16v-5" /><path d="M12 8h.01" /></svg>
          <div>
            <span className="callout-title">The client sends your object unchanged.</span>
            <p>It validates the structure and does not rewrite, trim or truncate content. Content limits are enforced by the instance and surface later as typed errors or as publication failures. <code>{"baseUrl"}</code> must be <code>{"https"}</code> outside loopback; plaintext <code>{"http"}</code> is accepted for <code>{"localhost"}</code> and <code>{"127.0.0.1"}</code>.</p>
          </div>
        </div>

        <h2 id="read-the-result">Read the result back</h2>
        <p>A create receipt is not a delivery: the instance has accepted the post and queued a publication, and nothing has reached a platform. Wait for a terminal status, then check the publication.</p>
        <p>One read is enough to see where the post stands, and it is always safe to repeat:</p>
        <pre data-label="read-result.mjs"><code>{"import { SyndrooClient } from \"@syndroo/sdk\";\n\nconst syndroo = new SyndrooClient({\n  baseUrl: process.env.SYNDROO_BASE_URL,\n  apiKey: process.env.SYNDROO_API_KEY,\n});\n\nconst post = await syndroo.posts.get(process.argv[2]);\n\nconsole.log(post.status);\nfor (const publication of post.publications) {\n  console.log(\n    publication.platform,\n    publication.status,\n    publication.attempts,\n    publication.errorCode ?? \"-\",\n    publication.errorAmbiguous === true ? \"unknown\" : \"\",\n  );\n}"}</code></pre>
        <p>Recent posts are <code>{"await syndroo.posts.list({ limit: 5 })"}</code>, where <code>{"limit"}</code> is <code>{"1"}</code> to <code>{"100"}</code>; it resolves to an array of post summaries.</p>
        <p><code>{"posts.wait"}</code> polls for you until the status is <code>{"published"}</code>, <code>{"partial"}</code> or <code>{"failed"}</code>, or until <code>{"timeoutMs"}</code> elapses. Reading never creates, cancels or resends anything, so a timeout leaves the server-side work running: <code>{"SyndrooWaitTimeoutError"}</code> keeps <code>{"postId"}</code>, <code>{"lastStatus"}</code>, <code>{"lastPost"}</code> and <code>{"lastError"}</code> so you can resume instead of starting over.</p>
        <p><code>{"timeoutMs"}</code> defaults to <code>{"60000"}</code>, <code>{"pollIntervalMs"}</code> to <code>{"250"}</code>, and <code>{"maxPollIntervalMs"}</code> to <code>{"2000"}</code>, with bounded exponential backoff between reads. The poll itself parks on a timer the runtime is allowed to ignore, so in a short script whose only remaining work is that wait, Node can exit before the deadline; a long-lived process such as a server or a job runner keeps it alive. If your script may exit early, poll <code>{"posts.get"}</code> yourself instead of relying on <code>{"wait"}</code>.</p>

        <h2 id="idempotency">Idempotency and unknown outcomes</h2>
        <p>The SDK performs exactly one HTTP request per call. It never retries a write, because a silent retry can duplicate a post.</p>
        <div className="table-wrap">
          <table>
            <caption>What to do after a failed call, decided by <code>requestMayHaveBeenApplied</code>.</caption>
            <thead>
              <tr><th scope="col">The error</th><th scope="col">Flag</th><th scope="col">What to do</th></tr>
            </thead>
            <tbody>
              <tr>
                <th scope="row">A <code>{"4xx"}</code> decision such as <code>{"UNAUTHORIZED"}</code> or <code>{"PLATFORM_NOT_CONFIGURED"}</code></th>
                <td><code>{"false"}</code></td>
                <td>Nothing was created. Fix the cause and send a new request. A different post may use a different key.</td>
              </tr>
              <tr>
                <th scope="row">A timeout, an abort, a network failure, or a <code>{"5xx"}</code> after a create</th>
                <td><code>{"true"}</code></td>
                <td>The write may have landed. Look the post up with <code>{"posts.list"}</code>, or repeat the identical request with the same <code>{"idempotencyKey"}</code>. Never with a new key and never with different content.</td>
              </tr>
            </tbody>
          </table>
        </div>
        <p>Server codes such as <code>{"IDEMPOTENCY_CONFLICT"}</code> (<code>{"409"}</code>) mean the key was already used with a different request. Replaying the original body returns the original result instead. The client never follows redirects: a <code>{"3xx"}</code> becomes a <code>{"SyndrooApiError"}</code> with code <code>{"REDIRECT_NOT_FOLLOWED"}</code>, so the <code>{"Authorization"}</code> header can never be forwarded to another host. Point <code>{"baseUrl"}</code> at the final API origin.</p>

        <h2 id="errors">Errors you can branch on</h2>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">Class</th><th scope="col">Raised when</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row"><code>{"SyndrooConfigError"}</code></th><td>The client configuration is unusable. No request is made.</td></tr>
              <tr><th scope="row"><code>{"SyndrooValidationError"}</code></th><td>An argument cannot become a valid request. No request is made.</td></tr>
              <tr><th scope="row"><code>{"SyndrooApiError"}</code></th><td>The instance answered with a documented error envelope. Carries <code>{"status"}</code>, <code>{"code"}</code>, <code>{"retryable"}</code> and <code>{"retryAfterMs"}</code>.</td></tr>
              <tr><th scope="row"><code>{"SyndrooResponseError"}</code></th><td>The answer was not the documented JSON contract.</td></tr>
              <tr><th scope="row"><code>{"SyndrooAbortError"}</code>, <code>{"SyndrooTimeoutError"}</code></th><td>You aborted through an <code>{"AbortSignal"}</code>, or the per-request deadline elapsed.</td></tr>
              <tr><th scope="row"><code>{"SyndrooNetworkError"}</code></th><td>No HTTP response arrived.</td></tr>
              <tr><th scope="row"><code>{"SyndrooWaitTimeoutError"}</code></th><td><code>posts.wait</code> hit its deadline before a terminal status.</td></tr>
            </tbody>
          </table>
        </div>
        <p>Every failure is a <code>{"SyndrooError"}</code>; use <code>{"isSyndrooError()"}</code> to narrow, or the exported classes directly. API errors carry no retry attempt of their own, only <code>{"retryable"}</code> and <code>{"retryAfterMs"}</code>, so your own policy decides what happens next.</p>

        <h2 id="acceptance">What success looks like</h2>
        <p>One post, one platform, and a result you can state without guessing. This is the same acceptance bar in the agent and CLI paths.</p>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">Outcome</th><th scope="col">How you know</th><th scope="col">What it means</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row">Accepted</th><td><code>{"posts.create"}</code> returned a receipt</td><td>The instance stored the post and queued a publication. Nothing has reached a platform.</td></tr>
              <tr><th scope="row">Delivered</th><td><code>{"post.status"}</code> is <code>{"published"}</code></td><td>Every selected platform confirmed. With one platform selected, that platform published.</td></tr>
              <tr><th scope="row">Failed</th><td><code>{"post.status"}</code> is <code>{"failed"}</code> or <code>{"partial"}</code>, with <code>{"errorAmbiguous"}</code> <code>{"false"}</code></td><td>Stopped after a terminal failure or an exhausted retry budget. Read <code>{"errorCode"}</code>, <code>{"errorMessage"}</code> and <code>{"attempts"}</code>.</td></tr>
              <tr><th scope="row">Unknown</th><td><code>{"requestMayHaveBeenApplied"}</code> is <code>{"true"}</code>, or a publication has <code>{"errorAmbiguous"}</code> <code>{"true"}</code></td><td>The write may have landed. Query with the original key and check the platform account by hand.</td></tr>
            </tbody>
