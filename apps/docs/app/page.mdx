        <h2 id="what-is-syndroo">What Syndroo is</h2>
        <p>Syndroo is a small npm-workspaces monorepo with a Worker in front of Cloudflare D1, Queues and a Cron Trigger. It accepts immediate or scheduled posts, keeps one publication row per platform, and reports each platform's own outcome.</p>
        <ul>
          <li><strong>HTTP API service.</strong> There is no dashboard, no account with the project, and no hosted service. You deploy the Worker, then call its URL from <code>{"curl"}</code>, an agent, a script or your own application.</li>
          <li><strong>Self-hosted.</strong> You own the Cloudflare account, D1 database, Queue, Cron Trigger and platform credentials.</li>
          <li><strong>Text only.</strong> Every adapter in this candidate publishes text. Media, per-request authors, OAuth login flows and token refresh are outside this version, so credential renewal is your job.</li>
          <li><strong>One public package, not published yet.</strong> <code>{"@syndroo/cloudflare-worker"}</code> is the only public package, and this candidate has not been published. The other workspace packages, including <code>{"@syndroo/core"}</code>, are internal implementations rather than public SDKs.</li>
          <li><strong>No Syndroo skill, plugin or MCP server.</strong> Agent setup means wiring your own client to the documented HTTP API; nothing is installable from the project yet.</li>
        </ul>

        <h2 id="how-it-runs">How it runs</h2>
        <p>The deployed Worker is the whole runtime. It keeps a Bearer-authenticated HTTP surface in front of D1 and a Queue producer, and it handles two background paths.</p>
        <ol className="steps">
          <li>
            <h3 id="admission">Admission</h3>
            <p><code>{"POST /v1/posts"}</code> validates the request and the platform configuration, then writes the post and one publication row per selected platform into D1. The reply is HTTP <code>{"202"}</code> with <code>{"status: \"queued\""}</code> or <code>{"\"scheduled\""}</code>.</p>
          </li>
          <li>
            <h3 id="delivery">Delivery</h3>
            <p>Immediate posts go to Cloudflare Queues. A Queue consumer claims one publication atomically before the outbound platform request, so one platform's failure does not stop the others.</p>
          </li>
          <li>
            <h3 id="scheduling">Scheduling and recovery</h3>
            <p>A Cron Trigger scans every 15 minutes for due posts and for stale jobs. A scheduled time in the past is handled as an immediate post.</p>
          </li>
          <li>
            <h3 id="inspection">Inspection</h3>
            <p><code>{"GET /v1/posts"}</code> and <code>{"GET /v1/posts/<id>"}</code> read the stored state, including one publication entry per platform with its status, error code and identifier.</p>
          </li>
        </ol>
        <p>Read <a href="/concepts/">Delivery and guarantees</a> before you build automation on top of the API. Queue delivery is at least once, retries are bounded, and an ambiguous platform result is never resent automatically.</p>
