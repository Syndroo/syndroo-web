        <h1 id="http-api">HTTP API</h1>
        <p className="lede">The 0.2.0-rc.1 candidate is one Bearer-authenticated HTTP API. It accepts immediate or scheduled posts, returns stored status, and reports per-platform outcomes. There is no dashboard in this candidate.</p>

        <h2 id="base-url">Base URL and headers</h2>
        <p>Every path below is relative to your deployed Worker URL, for example <code>{"https://your-worker.your-subdomain.workers.dev"}</code>. When you run locally the base URL is <code>{"http://localhost:8787"}</code>.</p>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">Header</th><th scope="col">Required</th><th scope="col">Notes</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row"><code>{"Authorization"}</code></th><td>On every <code>{"/v1/"}</code> request</td><td><code>{"Bearer <SYNDROO_API_KEY>"}</code>. The health endpoint does not require it.</td></tr>
              <tr><th scope="row"><code>{"Content-Type"}</code></th><td>On <code>{"POST"}</code></td><td>Must be <code>{"application/json"}</code>. Anything else returns <code>{"415"}</code>.</td></tr>
              <tr><th scope="row"><code>{"Idempotency-Key"}</code></th><td>Recommended on <code>{"POST"}</code></td><td>Optional. 1 to 128 letters, digits, dots, underscores, colons, or hyphens.</td></tr>
            </tbody>
          </table>
        </div>

        <h2 id="authentication">Authentication</h2>
        <p>The Worker compares the supplied Bearer token against <code>{"SYNDROO_API_KEY"}</code> using a constant-time digest comparison. A missing or incorrect token returns HTTP <code>{"401"}</code> with code <code>{"UNAUTHORIZED"}</code>.</p>
        <div className="callout info">
          <svg viewBox="0 0 24 24" fill="none" stroke="currentColor" strokeWidth="2" strokeLinecap="round" aria-hidden="true"><circle cx="12" cy="12" r="9" /><path d="M12 16v-5" /><path d="M12 8h.01" /></svg>
          <div>
            <span className="callout-title">Treat the API key like a password.</span>
            <p>Anyone who has it can publish through your Worker. Do not commit it, and do not put it in client-side code that other people can read.</p>
          </div>
        </div>

        <h2 id="create-a-post">Create a post</h2>
        <pre data-label="POST /v1/posts"><code>{"POST /v1/posts\nAuthorization: Bearer $SYNDROO_API_KEY\nContent-Type: application/json\nIdempotency-Key: example-post-001"}</code></pre>
        <p>A new post returns HTTP <code>{"202"}</code> with <code>{"status"}</code> set to <code>{"queued"}</code> or <code>{"scheduled"}</code>. The reply is an acceptance receipt: it does not confirm platform success, and <code>{"queued"}</code> means the stored post still has publications waiting. Read <code>{"publications"}</code> to see which platforms are already done.</p>

        <h3 id="request-fields">Request body fields</h3>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">Field</th><th scope="col">Type</th><th scope="col">Required</th><th scope="col">Notes</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row"><code>{"content"}</code></th><td>string</td><td>Yes</td><td>The shared, non-empty post text. The API caps content at 10,000 code points; individual platform limits are tighter and can fail the publication later.</td></tr>
              <tr><th scope="row"><code>{"platforms"}</code></th><td>{"string[]"}</td><td>Yes</td><td>A non-empty array without duplicates. Supported names are <code>{"threads"}</code>, <code>{"bluesky"}</code>, <code>{"x"}</code>, <code>{"tumblr"}</code>, and <code>{"linkedin"}</code>. Each selected platform must be configured, or the request fails with <code>{"422"}</code>.</td></tr>
              <tr><th scope="row"><code>{"overrides"}</code></th><td>object</td><td>No</td><td>Per-platform text. Each key must be one of the selected platforms, and each value takes a single <code>{"content"}</code> string, for example <code>{"{\"bluesky\": {\"content\": \"Text for Bluesky\"}}"}</code>.</td></tr>
              <tr><th scope="row"><code>{"scheduledAt"}</code></th><td>string</td><td>No</td><td>An ISO date-time with an explicit timezone, preferably UTC with <code>{"Z"}</code>. A future value creates status <code>{"scheduled"}</code>; a past value is handled as an immediate post.</td></tr>
            </tbody>
          </table>
        </div>

        <h3 id="create-example">Example request</h3>
        <div data-code-scope="publish">
          <pre data-label="POST /v1/posts"><code>{"curl -X POST \"$SYNDROO_URL/v1/posts\" \\\n  -H \"Authorization: Bearer $SYNDROO_API_KEY\" \\\n  -H \"Content-Type: application/json\" \\\n  -H \"Idempotency-Key: example-post-001\" \\\n  --data '{\n    \"content\": \"Hello from Syndroo on Threads\",\n    \"platforms\": [\"threads\", \"bluesky\"],\n    \"overrides\": {\n      \"bluesky\": { \"content\": \"Hello from Syndroo on Bluesky\" }\n    }\n  }'"}</code></pre>
        </div>
        <p>This command publishes a real post once those platform credentials are configured.</p>

        <h3 id="create-responses">Create responses</h3>
        <p>Immediate post, HTTP <code>{"202"}</code>:</p>
        <pre data-label="202 Accepted"><code>{"{\n  \"id\": \"post_...\",\n  \"status\": \"queued\"\n}"}</code></pre>
        <p>Scheduled post, HTTP <code>{"202"}</code>:</p>
        <pre data-label="202 Accepted"><code>{"{\n  \"id\": \"post_...\",\n  \"status\": \"scheduled\",\n  \"scheduledAt\": \"2030-01-02T03:04:05.000Z\"\n}"}</code></pre>
        <p>Idempotent replay of an identical request, HTTP <code>{"200"}</code>:</p>
        <pre data-label="200 OK"><code>{"{\n  \"id\": \"post_...\",\n  \"status\": \"queued\",\n  \"replayed\": true\n}"}</code></pre>

        <h3 id="idempotency-header">Idempotency-Key</h3>
        <p><code>{"Idempotency-Key"}</code> is optional but recommended for deployment automation. Use a stable key for one logical post.</p>
        <ul>
          <li>Repeating the same request with the same key returns the original post with <code>{"replayed: true"}</code> and HTTP <code>{"200"}</code>.</li>
          <li>Reusing the key with different content returns HTTP <code>{"409"}</code> and code <code>{"IDEMPOTENCY_CONFLICT"}</code>.</li>
          <li>A malformed key, such as one containing spaces or more than 128 characters, returns HTTP <code>{"400"}</code> and code <code>{"INVALID_REQUEST"}</code>.</li>
          <li>While maintenance mode is enabled, an authenticated <code>{"POST"}</code> is rejected before the key is read, so nothing is recorded.</li>
        </ul>
        <p>Read <a href="/concepts/#idempotency">Idempotency</a> for the delivery reasoning behind this header.</p>

        <h2 id="get-a-post">Check a post</h2>
        <pre data-label="GET /v1/posts/{id}"><code>{"curl \\\n  -H \"Authorization: Bearer $SYNDROO_API_KEY\" \\\n  \"$SYNDROO_URL/v1/posts/post_...\""}</code></pre>
        <p>A found post returns HTTP <code>{"200"}</code>. An unknown id returns HTTP <code>{"404"}</code> with code <code>{"POST_NOT_FOUND"}</code>.</p>
        <pre data-label="200 OK"><code>{"{\n  \"id\": \"post_...\",\n  \"content\": \"Hello from Syndroo\",\n  \"platforms\": [\"bluesky\"],\n  \"status\": \"published\",\n  \"createdAt\": \"2030-01-02T03:04:05.000Z\",\n  \"publications\": [\n    {\n      \"id\": \"pub_...\",\n      \"postId\": \"post_...\",\n      \"platform\": \"bluesky\",\n      \"provider\": \"bluesky-native\",\n      \"content\": \"Hello from Syndroo\",\n      \"status\": \"published\",\n      \"attempts\": 1,\n      \"externalId\": \"bafyre...\",\n      \"externalUrl\": \"https://bsky.app/profile/.../post/...\",\n      \"errorAmbiguous\": false,\n      \"createdAt\": \"2030-01-02T03:04:05.000Z\",\n      \"publishedAt\": \"2030-01-02T03:04:06.000Z\"\n    }\n  ]\n}"}</code></pre>
        <p>If the post is still <code>{"queued"}</code> or <code>{"publishing"}</code>, wait briefly and request the same URL again. If it is <code>{"failed"}</code>, inspect <code>{"errorCode"}</code>, <code>{"errorMessage"}</code>, and <code>{"errorAmbiguous"}</code> in the publication entry.</p>

        <p><code>{"limit"}</code> is optional, defaults to <code>{"50"}</code>, and must be an integer from <code>{"1"}</code> to <code>{"100"}</code>. Anything else returns HTTP <code>{"400"}</code> with code <code>{"INVALID_REQUEST"}</code>.</p>

        <h2 id="limits">Limits</h2>
        <div className="table-wrap">
          <table>
            <thead>
              <tr><th scope="col">Area</th><th scope="col">Limit</th></tr>
            </thead>
            <tbody>
              <tr><th scope="row">Request body</th><td>64 KiB.</td></tr>
              <tr><th scope="row">Shared content</th><td>10,000 code points at the API layer.</td></tr>
              <tr><th scope="row">Threads</th><td>500 Unicode characters. Text only.</td></tr>
              <tr><th scope="row">Bluesky</th><td>The candidate enforces 300 Unicode code points and 3,000 UTF-8 bytes before the network call; the official lexicon counts 300 graphemes, so the guard can be stricter for text built from combining marks or multi-code-point emoji.               <tr><th scope="row">X</th><td>280 weighted characters, validated with <code>{"twitter-text"}</code> before network access. Premium long posts are outside this version.</td></tr>

              <tr><th scope="row">Scheduling cadence</th><td>Cron looks for due posts every 15 minutes. Queue and platform time are added on top, so <code>{"scheduledAt"}</code> is the earliest intended publication time and no completion bound is promised.</td></tr>

        <h2 id="scheduling">Scheduling</h2>
        <p>Send <code>{"scheduledAt"}</code> as an ISO date-time with an explicit timezone. UTC with <code>{"Z"}</code> avoids ambiguity between machines.</p>
        <pre data-label="POST /v1/posts"><code>{"{\n  \"content\": \"Shared fallback\",\n  \"platforms\": [\"bluesky\"],\n  \"overrides\": {\n    \"bluesky\": { \"content\": \"Scheduled Bluesky post\" }\n  },\n  \"scheduledAt\": \"2030-01-02T03:04:05.000Z\"\n}"}</code></pre>
        <p>The accepted response returns status <code>{"scheduled"}</code>. Scheduling stays inside Syndroo; the platform's own queue is not used. An authenticated <code>{"GET"}</code> on the returned id shows the same post before and after it is due.</p>

        <h2 id="maintenance">Maintenance mode</h2>
        <p><code>{"SYNDROO_MAINTENANCE"}</code> is an optional, non-secret Worker variable. Only the exact string <code>{"true"}</code> enables it; <code>{"false"}</code> or an unset variable keeps normal operation.</p>
        <ul>
          <li>An authenticated <code>{"POST /v1/posts"}</code> returns HTTP <code>{"503"}</code> with code <code>{"SERVICE_UNAVAILABLE"}</code>.</li>
          <li>The rejection happens after Bearer authentication and before the request body, the idempotency key, or the database is read, so maintenance never creates a post and never records a key.</li>
          <li><code>{"GET /health"}</code> and the authenticated <code>{"GET /v1/posts"}</code> and <code>{"GET /v1/posts/<id>"}</code> queries keep working.</li>
          <li>Requests without a valid Bearer token still return <code>{"401"}</code>.</li>
          <li>Maintenance is admission control only. It does not pause Queue consumers or the Cron Trigger, so accepted work, scheduled work, and stale-job recovery continue to run.</li>
        </ul>
        <pre data-label="503 Service Unavailable"><code>{"{\n  \"error\": {\n    \"code\": \"SERVICE_UNAVAILABLE\",\n    \"message\": \"Syndroo is in maintenance mode and is not accepting new posts; retry later with the same Idempotency-Key and request body\"\n  }\n}"}</code></pre>
